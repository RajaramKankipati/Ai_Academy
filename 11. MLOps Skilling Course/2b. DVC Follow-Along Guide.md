# DVC Follow-Along Guide

A hands-on, terminal-based companion to
[`2. Implementing Data Versioning Using DVC.ipynb`](2.%20Implementing%20Data%20Versioning%20Using%20DVC.ipynb).
That notebook simulates the whole workflow in Python for you to read end to end;
this guide is the same journey run for real, one command at a time, in your own
terminal.

Three parts:

1. **DVC Basics** — init a project, version a file, push/pull it, roll back a version.
2. **Data Management Tutorial** — pulling data from someone else's DVC-tracked repo.
3. **Pipeline Tutorial** — chain multiple stages into a reproducible pipeline.

## Git vs. DVC — why you need both

**Git** is built to version *text*: it stores every change to your code as a compact,
diffable delta, and that only works efficiently because source files are small and
line-based. **DVC (Data Version Control)** exists because datasets and model files
don't fit that model — they're often huge, binary, and change in ways a line-by-line
diff can't summarize. Committing a multi-gigabyte CSV straight into Git would bloat
the repository forever, since Git keeps every version of every file ever committed.

DVC's fix: it stores the actual data in a separate location (a **remote** — local
folder, S3, GCS, DagsHub, etc.) and asks Git to track a tiny **pointer file** instead
(just a hash and file size). So in this workflow:

- **Git** tracks your code, your `.dvc` pointer files, and your pipeline definitions
  (`dvc.yaml`, `dvc.lock`) — everything small and text-based.
- **DVC** tracks the actual data and model bytes, using the same commands feel
  (`add`, `push`, `checkout`) but operating on its own remote storage.

A Git commit tells you *which version* of a pointer file you're on; `dvc checkout`
then syncs your actual working files to match that pointer. The two tools always
move together — that's why nearly every step below is a `dvc` command immediately
followed by a `git` command.

## Part 1 — DVC Basics

1. Create a folder either in docs or desktop

```bash
mkdir dvc-project
```

This is just your project's home directory — everything else in this walkthrough
happens inside it.

2. Initialise git and dvc

```bash
git init -q
dvc init -q
```

`git init` starts version control for your code and pointer files. `dvc init` needs
an existing Git repo to hook into — it sets up DVC's own internal cache and config
folder (`.dvc/`) alongside it, since DVC always rides on top of Git rather than
replacing it.

3. Make a directory for storing the data

```bash
mkdir data
```

Keeping data in its own folder makes it easy to `.gitignore` and to point DVC
commands at consistently as the project grows.

4. Get the sample data downloaded from dvc registry

```bash
dvc get https://github.com/treeverse/dataset-registry \
          get-started/data.xml -o data/data.xml
```

`dvc get` fetches a single file that's tracked by DVC in another repository, without
cloning that whole repository — a fast way to grab one dataset out of a much larger
data registry.

5. Add the data file to the DVC

```bash
dvc add data/data.xml
```

This is the step that actually starts *versioning* the data: DVC moves the file's
contents into its local cache and generates a small pointer file next to it, so
future changes to `data.xml` can be tracked without ever putting the raw bytes into
Git.

6. Add the dvc file to the git

```bash
git add data/.gitignore data/dataset.csv.dvc
```

`dvc add` also writes a `.gitignore` entry so Git never tries to track the data file
directly — here you stage that `.gitignore` plus the pointer file, which is the only
part of this that Git needs to know about.

7. Commit them to the git

```bash
git commit -m "Add raw data"
```

This records, in Git history, that "this project now has a versioned dataset" — the
commit itself is tiny, since it's only committing the pointer, not the data.

8. Configure the dvc remote - it can be local, Cloud provider

```bash
dvc remote add -d storage dvc-remote
```

A remote is where the *actual data* lives once you push it — think of it as the DVC
equivalent of a Git remote like GitHub, except it stores full file contents rather
than commit history. It can be a local folder for testing or a real cloud bucket
(S3, GCS, Azure) for a team.

9. Commit the change in configuration

```bash
git commit .dvc/config -m "Configure dvc remote"
```

Remote configuration lives in `.dvc/config`, and that file is text, so Git tracks it
directly — committing it means anyone who clones this repo automatically knows
where to `dvc pull` the data from.

10. Push the changes to the DVC remote

```bash
dvc push
```

This is the step that actually uploads the tracked data to the remote you just
configured — until this runs, the data only exists in your local DVC cache.

11. Do the changes to the data file

Edit `data.xml` however you like — this step represents your data changing over
time, the same way editing a source file represents code changing over time.

12. Add file to the dvc

```bash
dvc add data/data.xml
```

Re-running `dvc add` after a change updates the pointer file to reflect the new
version of the data — conceptually the same as `git add` picking up a modified file.

13. Commit changes to git

```bash
git commit data/data.xml.dvc -m "Dataset updates"
```

Committing the updated pointer records, in Git history, exactly when the dataset
changed and to what — this is what makes the dataset's history reviewable the same
way code history is.

14. Checkout the git previous commit versions

```bash
git checkout HEAD^1 data/data.xml.dvc
```

This rewinds the *pointer file* to the version it had one commit ago — it doesn't
touch the actual data yet, just tells Git "go back to referencing the older
version."

15. Checkout dvc

```bash
dvc checkout
head -1 data/data.xml
```

`dvc checkout` is what actually syncs your working data file to match whatever
version the pointer (just rewound in step 14) refers to — this is the step that
performs the real rollback. `head -1` is just a quick sanity check that the file's
contents really did revert.

16. Push the changes to the github remote

```bash
git remote add origin <git repository>
```

Registers a remote Git repository (e.g. on GitHub) so your code and pointer-file
history can be pushed and shared — this is the Git-side counterpart to step 8's DVC
remote, and both are needed for someone else to fully reproduce your project.

## Part 2 — Data Management Tutorial

Once data is DVC-tracked somewhere, these are the ways to pull it into another
project, each suited to a different situation:

```bash
dvc list https://github.com/treeverse/dataset-registry get-started
```

Lists what's available at that path in a DVC-tracked repository without downloading
anything — useful for browsing a data registry before deciding what you need.

```bash
dvc get https://github.com/treeverse/dataset-registry \
          use-cases/cats-dogs
```

Downloads a one-time copy of the data with no ongoing link back to the source — if
the source repository updates later, this copy won't know and won't update.

```bash
dvc import https://github.com/treeverse/dataset-registry \
             get-started/data.xml -o data/data.xml
```

Also downloads a copy, but additionally records *which version* of the source
repository it came from — this is what makes the next command possible.

```bash
dvc update data/data.xml.dvc
```

Because the data was brought in with `dvc import` (not `dvc get`), DVC knows where
it originally came from and can check for and pull down a newer version — keeping
your local copy in sync with the upstream source on demand.

## Part 3 — Pipeline Tutorial

A single versioned file (Parts 1-2) is enough for one dataset, but a real project
usually has multiple processing stages that depend on each other. This part chains
several steps together into a DVC **pipeline**, so the whole thing can be re-run
reproducibly with one command.

```bash
git init -q
dvc init -q

virtualenv myenv
source myenv/bin/activate


wget https://code.dvc.org/get-started/code.zip
unzip code.zip && rm -f code.zip

dvc get https://github.com/treeverse/dataset-registry \
          get-started/data.xml -o data/data.xml
dvc add data/data.xml

pip install -r src/requirements.txt
```

Same Git/DVC init as Part 1, plus three new things: a virtual environment to keep
this project's Python packages isolated, the tutorial's example source code
(`prepare.py`, `featurization.py`, `train.py` — a small pipeline that cleans text,
extracts features, and trains a model), and that code's own dependencies installed
from `requirements.txt`.

Add stages

```bash
dvc stage add -n prepare \
                -p prepare.seed,prepare.split \
                -d src/prepare.py -d data/data.xml \
                -o data/prepared \
                python src/prepare.py data/data.xml

dvc stage add -n featurize \
                -p featurize.max_features,featurize.ngrams \
                -d src/featurization.py -d data/prepared \
                -o data/features \
                python src/featurization.py data/prepared data/features

dvc stage add -n train \
                -p train.seed,train.n_est,train.min_split \
                -d src/train.py -d data/features \
                -o model.pkl \
                python src/train.py data/features model.pkl
```

Each `dvc stage add` registers one step of the pipeline: `-d` lists what it depends
on (so DVC knows when it needs to re-run), `-o` lists what it produces, and `-p`
lists which config parameters it's sensitive to. Notice `featurize` depends on
`data/prepared` (the *output* of `prepare`), and `train` depends on `data/features`
(the *output* of `featurize`) — that chain is what lets DVC figure out the correct
run order automatically. Running these writes a `dvc.yaml` file describing all three
stages.

```bash
git add .gitignore data/.gitignore dvc.yaml
git commit -m "pipeline defined"
```

This commits the *definition* of the pipeline (the stages and how they connect) to
Git — at this point the pipeline exists on paper but hasn't actually been run yet.

```bash
dvc repro
```

This is what actually executes the pipeline: DVC runs every stage whose inputs have
changed (on a first run, that's all of them, in dependency order) and records the
exact input/output hashes it produced in a new `dvc.lock` file.

```bash
git add dvc.lock && git commit -m "first pipeline repro"
```

Committing `dvc.lock` records, in Git history, the exact reproducible result of that
pipeline run — anyone who checks out this commit and runs `dvc repro` again should
get identical outputs, as long as the underlying data and code haven't changed.

```bash
dvc dag
```

Prints the stage dependency graph in your terminal — a quick way to visually confirm
the `-d`/`-o` wiring from the `dvc stage add` commands produced the pipeline shape
you intended.
