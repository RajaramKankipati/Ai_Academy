## Overview

You will build a mushroom classifier (edible vs poisonous) and a GitHub Actions pipeline that retrains and tests it on every pull request. A model that falls below the agreed accuracy cannot be merged into `main`.

By the end, you will be able to:

- Set up a reproducible Python project with a virtual environment and pinned dependencies.
- Write data tests and model **quality gate** tests with pytest.
- Write a GitHub Actions workflow that lints, tests, trains and uploads the model.
- Use branch protection so a failing quality gate blocks the merge.

**Prerequisites:** Python 3.11, Git, a GitHub account, and the GitHub CLI (`gh`). Install `gh` from [cli.github.com](https://cli.github.com) and run `gh auth login` once.

**Dataset:** [UCI Mushroom](https://archive.ics.uci.edu/dataset/73/mushroom), 8,124 mushrooms with 22 categorical features. It is downloaded automatically by the code; you do not need to download it by hand.

## Step 1: Create the project and a virtual environment

```bash

```

To leave the environment later, run `deactivate`.

## Step 2: Install the dependencies

Create a file called `requirements.txt` in the project root. Each version is **pinned** with `==`, so your laptop and the CI server install exactly the same packages.

```text
scikit-learn==1.5.2
pandas==2.2.3
joblib==1.4.2
ucimlrepo==0.0.7
pytest==8.3.3
ruff==0.6.9
```

| Package | Why we need it |
| --- | --- |
| scikit-learn | Random forest model, train/test split, cross-validation, metrics |
| pandas | Tables of data and one-hot encoding |
| joblib | Saves the trained model to a file |
| ucimlrepo | Downloads the Mushroom dataset from UCI |
| pytest | Runs the tests |
| ruff | Linter: catches unused imports, syntax errors and style issues |

Install them with the venv active:

```bash
python -m pip install --upgrade pip
pip install -r requirements.txt
```

Why pin? Without pins, the CI server installs whatever is newest on the day it runs. A new pandas release could then change your results or break your code, and "it works on my machine" stops being true.

## Step 4: Load and clean the data (src/data.py)

This file downloads the dataset and turns it into numbers a model can learn from.

```python
"""Load and preprocess the UCI Mushroom dataset."""
import pandas as pd
from ucimlrepo import fetch_ucirepo

RANDOM_STATE = 42
DROP_COLUMNS = ["veil-type"]  # constant, carries no information


def load_raw():
    ds = fetch_ucirepo(id=73)
    X = ds.data.features.copy()
    y = ds.data.targets.iloc[:, 0].copy()
    return X, y


def preprocess(X, y):
    X = X.drop(columns=[c for c in DROP_COLUMNS if c in X.columns])
    # '?' -> NaN -> explicit "unknown" category. Never drop rows: the missing
    # values are concentrated in one class and dropping them biases the sample.
    X = X.fillna("unknown")
    X = pd.get_dummies(X)
    y = (y == "p").astype(int)  # 1 = poisonous
    return X, y


def load_mushroom():
    return preprocess(*load_raw())
```

What each part does:

- **`RANDOM_STATE = 42`**: one fixed seed shared by every random step, so every run gives the same result. CI depends on this.
- **`load_raw()`**: downloads dataset 73 from UCI. `X` holds the 22 features; `y` holds the label, `e` (edible) or `p` (poisonous).
- **Drop `veil-type`**: it has the same value in every row, so it cannot help the model.
- **`fillna("unknown")`**: the `stalk-root` column has missing values. We keep those rows and mark the value as `unknown`. Most of the missing rows are poisonous, so deleting them would remove poisonous examples and bias the data.
- **`pd.get_dummies(X)`**: one-hot encoding. A column like `cap-shape` with values `x`, `b`, `f` becomes three True/False columns: `cap-shape_x`, `cap-shape_b`, `cap-shape_f`.
- **`y == "p"`**: turns the label into 1 for poisonous and 0 for edible.

`load_raw()` (download) and `preprocess()` (clean) are kept as separate functions so we can test the cleaning on small fake data without the internet.

## Step 5: Train the model (src/train.py)

This file trains a random forest, measures it, and writes two files: `model.joblib` (the trained model) and `metrics.json` (its scores). The tests in Step 6 read `metrics.json`.

```python
"""Train the mushroom classifier and write metrics.json."""
import json
import sys

import joblib
from sklearn.ensemble import RandomForestClassifier
from sklearn.metrics import accuracy_score, f1_score, recall_score
from sklearn.model_selection import StratifiedKFold, cross_val_score, train_test_split

from src.data import RANDOM_STATE, load_mushroom

MAX_DEPTH = int(sys.argv[1]) if len(sys.argv) > 1 else None


def main():
    X, y = load_mushroom()
    X_tr, X_te, y_tr, y_te = train_test_split(
        X, y, test_size=0.25, random_state=RANDOM_STATE, stratify=y
    )

    model = RandomForestClassifier(
        n_estimators=100, max_depth=MAX_DEPTH, random_state=RANDOM_STATE, n_jobs=1
    )
    model.fit(X_tr, y_tr)
    pred = model.predict(X_te)

    # Shuffle: the UCI file is ordered, so unshuffled folds are skewed.
    folds = StratifiedKFold(n_splits=5, shuffle=True, random_state=RANDOM_STATE)
    cv = cross_val_score(model, X, y, cv=folds, scoring="accuracy", n_jobs=1)

    metrics = {
        "accuracy": round(float(accuracy_score(y_te, pred)), 4),
        "f1": round(float(f1_score(y_te, pred)), 4),
        "recall_poisonous": round(float(recall_score(y_te, pred)), 4),
        "cv_accuracy_mean": round(float(cv.mean()), 4),
        "cv_accuracy_std": round(float(cv.std()), 4),
        "n_train": len(X_tr),
        "n_features": int(X.shape[1]),
        "max_depth": MAX_DEPTH,
    }

    joblib.dump(model, "model.joblib")
    with open("metrics.json", "w") as f:
        json.dump(metrics, f, indent=2)
    print(json.dumps(metrics, indent=2))


if __name__ == "__main__":
    main()
```

What each part does:

- **`MAX_DEPTH`**: an optional command-line setting. `python -m src.train 5` limits each tree to depth 5; with no argument, trees grow fully.
- **`train_test_split(..., stratify=y)`**: keeps 25% of the data aside for testing. `stratify` keeps the same edible/poisonous ratio in both parts.
- **Accuracy, F1, recall**: scores on the held-out 25%. **Recall on poisonous** is the share of poisonous mushrooms the model catches. This is the one that matters most, because calling a poisonous mushroom edible is the dangerous mistake.
- **Cross-validation (`cv`)**: trains and scores the model 5 times on 5 different splits. The **standard deviation** tells us whether the score is stable or just lucky.
- **`metrics.json`**: the hand-off to the quality gate. Training and judging are separate steps, which keeps each one simple.

**Lesson from building this: always shuffle cross-validation folds.** The UCI file is sorted, so without `shuffle=True` some folds get a skewed mix of mushrooms. With plain `cv=5`, the fold scores were 0.84, 1.0, 1.0, 1.0 and 0.82 (std 0.084). With `StratifiedKFold(shuffle=True)`, all five folds scored 1.0 (std 0.0). The model was the same; only the evaluation was wrong.

## Step 6: Write the tests

We write two kinds of tests. **Data tests** check the cleaning code and run in under a second on small made-up data. **Model tests** (the quality gate) check the scores in `metrics.json` after training.

### tests/test\_data.py

```python
import numpy as np
import pandas as pd

from src.data import preprocess


def make_raw():
    X = pd.DataFrame({
        "cap-shape": ["x", "b", "x", "f"],
        "stalk-root": ["e", np.nan, np.nan, "c"],
        "veil-type": ["p", "p", "p", "p"],
    })
    y = pd.Series(["e", "p", "p", "e"])
    return X, y


def test_drops_constant_veil_type():
    X, _ = preprocess(*make_raw())
    assert not any(c.startswith("veil-type") for c in X.columns)


def test_missing_values_become_unknown_category_without_dropping_rows():
    X, y = preprocess(*make_raw())
    assert len(X) == 4 and len(y) == 4
    assert "stalk-root_unknown" in X.columns
    assert X["stalk-root_unknown"].tolist() == [False, True, True, False]
    # Rows with missing values are all poisonous here; they must survive.
    assert y[X["stalk-root_unknown"]].tolist() == [1, 1]


def test_target_encoded_poisonous_as_one():
    _, y = preprocess(*make_raw())
    assert y.tolist() == [0, 1, 1, 0]


def test_works_when_veil_type_already_absent():
    X_raw, y_raw = make_raw()
    X, _ = preprocess(X_raw.drop(columns=["veil-type"]), y_raw)
    assert "cap-shape_x" in X.columns


def test_output_is_fully_numeric_with_no_nans():
    X, _ = preprocess(*make_raw())
    assert not X.isna().any().any()
    assert all(pd.api.types.is_bool_dtype(t) or pd.api.types.is_numeric_dtype(t)
               for t in X.dtypes)
```

`make_raw()` builds a 4-row fake dataset with the same problems as the real one: a constant column and missing values. Each test checks one rule of `preprocess()`. If someone later changes the cleaning and breaks a rule, the matching test fails and names it.

### tests/test\_model.py (the quality gate)

```python
import json
import os

import pytest

# Committed thresholds. Changing these requires a PR and a review -- that is the
# entire point: the bar moves deliberately, not because someone was in a hurry.
MIN_ACCURACY = 0.97
MIN_RECALL_POISONOUS = 0.98
MAX_CV_STD = 0.05

METRICS_PATH = "metrics.json"


@pytest.fixture(scope="module")
def metrics():
    if not os.path.exists(METRICS_PATH):
        pytest.fail(
            f"{METRICS_PATH} not found -- did the 'Train model' workflow step run?"
        )
    with open(METRICS_PATH) as f:
        return json.load(f)


def test_accuracy_above_threshold(metrics):
    assert metrics["accuracy"] >= MIN_ACCURACY, (
        f"QUALITY GATE FAILED: accuracy {metrics['accuracy']:.4f} "
        f"< threshold {MIN_ACCURACY}"
    )


def test_poisonous_recall_above_threshold(metrics):
    assert metrics["recall_poisonous"] >= MIN_RECALL_POISONOUS, (
        f"QUALITY GATE FAILED: recall on poisonous class "
        f"{metrics['recall_poisonous']:.4f} < threshold {MIN_RECALL_POISONOUS}. "
        f"Missing a poisonous mushroom is the costly error."
    )


def test_model_is_stable(metrics):
    assert metrics["cv_accuracy_std"] <= MAX_CV_STD, (
        f"cross-validation std {metrics['cv_accuracy_std']:.4f} exceeds "
        f"{MAX_CV_STD} -- the headline accuracy is not reproducible"
    )


def test_training_set_not_silently_shrunk(metrics):
    assert metrics["n_train"] == 6093, (
        f"expected 6093 training rows, got {metrics['n_train']} -- "
        f"a preprocessing change is dropping data"
    )
```

| Gate test | Rule | Why it matters |
| --- | --- | --- |
| `test_accuracy_above_threshold` | accuracy ≥ 0.97 | The model must be good overall |
| `test_poisonous_recall_above_threshold` | recall on poisonous ≥ 0.98 | Missing a poisonous mushroom is the dangerous error |
| `test_model_is_stable` | cross-validation std ≤ 0.05 | A good score must not be luck |
| `test_training_set_not_silently_shrunk` | exactly 6,093 training rows | 75% of 8,124 rows; fewer means a code change is dropping data |

The thresholds live in the code, not in someone's head. To lower the bar, a person must open a pull request that a reviewer can see and question. The `metrics` **fixture** loads `metrics.json` once and passes it to every test.

## Step 7: Run everything on your laptop first

Run the same four checks CI will run, in the same order. If they pass here, they should pass on GitHub.

```bash
# 1. Lint
ruff check src tests

# 2. Data tests
python -m pytest tests/test_data.py -v

# 3. Train (downloads the data the first time)
python -m src.train

# 4. Quality gate
python -m pytest tests/test_model.py -v
```

Expected training output:

```json
{
  "accuracy": 1.0,
  "f1": 1.0,
  "recall_poisonous": 1.0,
  "cv_accuracy_mean": 1.0,
  "cv_accuracy_std": 0.0,
  "n_train": 6093,
  "n_features": 116,
  "max_depth": null
}
```

Perfect scores are normal for this dataset. It is known to be fully separable, which is why it is a good teaching example.

**Run training as a module, always: `python -m src.train`, never `python src/train.py`.** Run as a plain file, Python cannot find the `src` package and fails with `ModuleNotFoundError: No module named 'src'`. The `-m` form runs from the project root, so `from src.data import ...` works.

If `ruff` reports import-order errors, fix them automatically with `ruff check --fix src tests`.

## Step 8: Write the GitHub Actions workflow

GitHub Actions runs your Step 7 checks automatically, on a fresh computer in the cloud, every time code is pushed or a pull request is opened.

&#91;embedded content: ci.yml as a flow · 7 steps, 1 gate, 2 outcomes\]

The cheap checks run first, so broken code fails in seconds; only the quality gate decides whether a working model is good enough.

### How GitHub Actions works

| Term | Meaning | In our project |
| --- | --- | --- |
| Workflow | A YAML file in `.github/workflows/` | `ci.yml` |
| Event (trigger) | What starts the workflow | A push to `main`, a pull request to `main`, or a manual click |
| Runner | A fresh virtual machine GitHub creates for the run and throws away afterwards | `ubuntu-latest` |
| Job | A group of steps that run on one runner | `test-and-gate` |
| Step | One command (`run:`) or a ready-made action (`uses:`) | Lint, test, train, gate, upload |
| Action | A reusable step someone else wrote | `actions/checkout`, `actions/setup-python` |
| Artifact | A file saved from the run that you can download later | `model.joblib`, `metrics.json` |

Steps run top to bottom. **If any step fails, the later steps are skipped and the job is marked failed** (red cross). That red cross is what blocks the merge in Step 10.

### .github/workflows/ci.yml

````yaml
name: ML CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read

jobs:
  test-and-gate:
    runs-on: ubuntu-latest
    timeout-minutes: 20

    steps:
      - name: Check out repository
        uses: actions/checkout@v4

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.11"
          cache: pip

      - name: Install dependencies
        run: |
          python -m pip install --upgrade pip
          pip install -r requirements.txt

      - name: Lint
        run: ruff check src tests

      - name: Data integrity tests
        run: python -m pytest tests/test_data.py -v

      - name: Train model
        run: python -m src.train

      - name: Show metrics in the run summary
        run: |
          echo '### Model metrics' >> $GITHUB_STEP_SUMMARY
          echo '```json' >> $GITHUB_STEP_SUMMARY
          cat metrics.json >> $GITHUB_STEP_SUMMARY
          echo '```' >> $GITHUB_STEP_SUMMARY

      - name: Quality gate
        id: gate
        run: python -m pytest tests/test_model.py -v

      - name: Upload model and metrics
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: model-${{ github.sha }}
          path: |
            model.joblib
            metrics.json
          retention-days: 14
````

### Line by line

- **`on:`** the three triggers. `workflow_dispatch` adds a **Run workflow** button in the Actions tab.
- **`permissions: contents: read`** the workflow can read the code and nothing else. Give workflows the least access they need.
- **`runs-on: ubuntu-latest`** a brand-new Linux machine every run. Nothing from your laptop is there, which is why `requirements.txt` must list every package.
- **`timeout-minutes: 20`** stops a stuck run from using up free minutes.
- **`actions/checkout`** copies your repository onto the runner.
- **`actions/setup-python`** installs Python 3.11. `cache: pip` reuses downloaded packages, so later runs are faster.
- **Lint, data tests** fast checks first. If the code is broken, we find out in seconds and never spend time training.
- **Train model** writes `model.joblib` and `metrics.json` on the runner.
- **`$GITHUB_STEP_SUMMARY`** text written to this file appears on the run's summary page, so reviewers see the metrics without opening logs.
- **Quality gate** the step that can fail the run because of model quality, not code errors.
- **`if: always()`** uploads the model and metrics even when the gate fails, so you can download them and see why.
- **`${{ github.sha }}`** the commit ID, so every run's artifact has a unique name.

## Step 10: Protect the main branch

So far CI only reports a red or green result. **Branch protection** turns that result into a rule: nothing reaches `main` unless the `test-and-gate` job passes.

Do this **after** the first run in Step 9 has finished, because GitHub only lets you require a check it has already seen run.

### Option A: on github.com

1. Open the repository, then **Settings → Branches → Add branch protection rule**.
2. Branch name pattern: `main`.
3. Tick **Require a pull request before merging**. Set required approvals to 1, or 0 if you work alone.
4. Tick **Require status checks to pass before merging** and **Require branches to be up to date before merging**.
5. Search for and add the check `test-and-gate`.
6. Click **Create**.

### Option B: from the terminal

Save the rule as `protection.json`:

```json
{
  "required_status_checks": {"strict": true, "contexts": ["test-and-gate"]},
  "enforce_admins": false,
  "required_pull_request_reviews": {"required_approving_review_count": 1},
  "restrictions": null
}
```

Apply it, then check it:

```bash
gh api -X PUT repos/:owner/:repo/branches/main/protection --input protection.json
gh api repos/:owner/:repo/branches/main/protection/required_status_checks
```

`gh` fills in `:owner/:repo` from your Git remote, so run this inside the project folder.

| Setting | Effect |
| --- | --- |
| `contexts: ["test-and-gate"]` | The job name from `ci.yml` must pass. The two names must match exactly. |
| `strict: true` | The pull request must be tested against the latest `main` |
| `required_approving_review_count: 1` | Someone other than the author must approve |
| `enforce_admins: false` | The repository owner can still override the rules |

**Working alone?** You cannot approve your own pull request. Either add a classmate as a collaborator, or set the review count to 0 and rely on the required check. Branch protection on **private** repositories needs a paid GitHub plan, so use a public repository for this lab.

## Step 11: Prove the gate works

Now break the gate on purpose and watch GitHub refuse the merge. We raise the accuracy bar to 1.01, which no model can reach.

1. Create a branch and change the threshold in `tests/test_model.py`:

   ```bash
   git checkout -b test-quality-gate
   ```

   ```python
   MIN_ACCURACY = 1.01  # TEMP: deliberately unreachable
   ```
2. Commit, push and open a pull request:

   ```bash
   git add tests/test_model.py
   git commit -m "Test quality gate with an unreachable threshold"
   git push -u origin test-quality-gate
   gh pr create --base main --title "[DO NOT MERGE] Test quality gate" --body "Expect the gate to fail."
   ```
3. Watch the check:

   ```bash
   gh pr checks --watch
   ```
4. Read the failure. Every step passes until **Quality gate**, which prints:

   ```text
   FAILED tests/test_model.py::test_accuracy_above_threshold - AssertionError: QUALITY GATE FAILED: accuracy 1.0000 < threshold 1.01
   1 failed, 3 passed
   ```
5. Open the pull request on github.com. The check shows a red cross and the **Merge** button is disabled. From the terminal:

   ```bash
   gh pr view --json mergeStateStatus     # "BLOCKED"
   ```
6. Clean up. Close the pull request without merging, so `main` keeps `MIN_ACCURACY = 0.97`:

   ```bash
   gh pr close --delete-branch
   git checkout main
   git branch -D test-quality-gate
   ```

This is the whole point of the lab: a model that is not good enough cannot reach `main`, and nobody has to remember to check.

## Common errors and fixes

Each of these came up while building this lab.

| Error | Cause | Fix |
| --- | --- | --- |
| `ModuleNotFoundError: No module named 'src'` | Ran `python src/train.py`, or ran plain `pytest` without `pytest.ini` | Run `python -m src.train`; add `pytest.ini` with `pythonpath = .` |
| `ModuleNotFoundError: No module named 'data'` | Changed the import to `from data import ...` to "fix" the error above | Keep `from src.data import ...` and run with `-m` |
| `test_model_is_stable` fails, std about 0.08 | Cross-validation folds not shuffled on a sorted dataset | Use `StratifiedKFold(n_splits=5, shuffle=True, random_state=RANDOM_STATE)` |
| Workflow never runs after a push | Local branch is `master`; the workflow listens only to `main` | `git branch -m master main`, then `git push -u origin main` |
| `metrics.json not found` | The Train step failed or was skipped | Read the Train step's log; fix that first |
| Lint fails in CI but not locally | Different ruff version on your laptop | Install from `requirements.txt` inside the venv |
| `test-and-gate` missing in branch protection settings | The workflow has never run yet | Push once, wait for the run, then add the rule |
| Pull request cannot be merged, no reviewer | 1 approval required, and you cannot approve your own pull request | Add a collaborator, or set required approvals to 0 |
| `gh pr create` says "No commits between main and ..." | The branch has no new commits | Make and commit a change first |
