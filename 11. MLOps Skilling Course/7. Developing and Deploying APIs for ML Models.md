# Developing and Deploying APIs for ML Models

## Overview

A model in a notebook is only useful to people who can run Python. A REST API makes it useful to anything that can send an HTTP request: a web page, a mobile app, another service, a `curl` command. In this session you put a heart-disease classifier behind a **FastAPI** service with strict input checks, tests, and **two API versions** running side by side, so the API can change without breaking existing clients.

By the end, you will be able to:

- Describe valid requests with **Pydantic** so bad input is rejected before it reaches the model.
- Build `/health`, `/v1/predict` and `/v2/predict` routes with FastAPI.
- Test an API with pytest and FastAPI's `TestClient`.
- Run the API with uvicorn and call it with `curl`.
- Tell a model version from an API version, and retire an old API version safely.

**Prerequisites:** Python 3.11 and a terminal. Everything runs locally.

**Dataset:** [UCI Heart Disease](https://archive.ics.uci.edu/dataset/45/heart+disease), Cleveland subset: 303 patients, 13 clinical measurements (age, blood pressure, cholesterol, max heart rate, ...) and a diagnosis. These are numbers a client really has to type into a request, which makes input checking concrete. It is downloaded automatically by the code.

## Step 4: Train the model (src/train.py)

```python
"""Train the heart disease classifier and save it to models/heart_disease.joblib."""
import joblib
from sklearn.ensemble import RandomForestClassifier
from sklearn.metrics import accuracy_score, roc_auc_score
from sklearn.model_selection import train_test_split
from ucimlrepo import fetch_ucirepo

MODEL_VERSION = "1.0.0"

df = fetch_ucirepo(id=45).data.original
print(f"{len(df)} patients, {df.isna().any(axis=1).sum()} with missing values")
df = df.dropna()
df["target"] = (df["num"] > 0).astype(int)      # 0 = no disease, 1-4 = disease
features = [c for c in df.columns if c not in ("num", "target")]
print(f"{len(df)} patients kept: {df['target'].sum()} with disease, "
      f"{(df['target'] == 0).sum()} without")

X_tr, X_te, y_tr, y_te = train_test_split(
    df[features], df["target"], test_size=0.2, random_state=42, stratify=df["target"]
)
model = RandomForestClassifier(n_estimators=200, max_depth=5, random_state=42)
model.fit(X_tr, y_tr)

proba = model.predict_proba(X_te)[:, 1]
print(f"accuracy: {accuracy_score(y_te, proba >= 0.5):.3f}")
print(f"ROC AUC : {roc_auc_score(y_te, proba):.3f}")

joblib.dump({"model": model, "features": features, "version": MODEL_VERSION},
            "models/heart_disease.joblib")
print(f"saved models/heart_disease.joblib (model version {MODEL_VERSION})")
```

```bash
python -m src.train
```

```text
303 patients, 6 with missing values
297 patients kept: 137 with disease, 160 without
accuracy: 0.833
ROC AUC : 0.945
saved models/heart_disease.joblib (model version 1.0.0)
```

- The original label `num` runs from 0 (healthy) to 4 (severe). We turn it into **0 = no disease, 1 = disease**, the usual way this dataset is used, and a simpler contract for API clients.
- 6 rows have missing values (`ca`, `thal`) and are dropped. Six rows is fine. In a real pipeline, log this count: if it were 20% of the data, you would fill the gaps instead of dropping rows.
- The classes are fairly balanced (137 vs 160), so accuracy is a fair headline number here.
- We save the **feature order** and a **model version** with the model. The API reads both.

## Step 5: Describe valid input (app/schemas.py)

A Pydantic model is both documentation and enforcement. FastAPI uses it to build the API docs **and** to check every request before your code runs.

```python
"""Request and response shapes. FastAPI validates every request against these."""
from typing import Literal

from pydantic import BaseModel, Field


class Patient(BaseModel):
    age: int = Field(..., ge=18, le=100, description="Age in years")
    sex: Literal[0, 1] = Field(..., description="1 = male, 0 = female")
    cp: Literal[1, 2, 3, 4] = Field(..., description="Chest pain type: 1 typical angina, "
                                    "2 atypical, 3 non-anginal, 4 none")
    trestbps: float = Field(..., ge=60, le=250, description="Resting blood pressure, mm Hg")
    chol: float = Field(..., ge=100, le=700, description="Serum cholesterol, mg/dl")
    fbs: Literal[0, 1] = Field(..., description="Fasting blood sugar > 120 mg/dl")
    restecg: Literal[0, 1, 2] = Field(..., description="Resting ECG result")
    thalach: float = Field(..., ge=60, le=250, description="Max heart rate achieved")
    exang: Literal[0, 1] = Field(..., description="Exercise-induced angina")
    oldpeak: float = Field(..., ge=0, le=10, description="ST depression from exercise")
    slope: Literal[1, 2, 3] = Field(..., description="Slope of peak exercise ST segment")
    ca: Literal[0, 1, 2, 3] = Field(..., description="Major vessels coloured by fluoroscopy")
    thal: Literal[3, 6, 7] = Field(..., description="3 normal, 6 fixed defect, "
                                   "7 reversible defect")


class PredictionV1(BaseModel):
    prediction: int
    probability: float
    label: str
    model_version: str


class BatchRequestV2(BaseModel):
    patients: list[Patient] = Field(..., min_length=1, max_length=100)


class PredictionV2(BaseModel):
    probability: float
    risk: Literal["low", "medium", "high"]


class BatchResponseV2(BaseModel):
    results: list[PredictionV2]
    model_version: str
```

What each part does:

- **`Field(..., ge=60, le=250)`**: the `...` means **required**; `ge`/`le` mean "greater/less than or equal". A blood pressure of 9999 (a unit mistake, or a "missing" placeholder) is rejected instead of producing a confident, meaningless prediction.
- **`Literal[1, 2, 3, 4]`**: only these exact values are allowed. Use this for coded categories. The allowed codes were taken from the real data: `cp` is 1–4, `slope` 1–3, and `thal` only ever 3, 6 or 7. A schema that guesses (e.g. `cp` 0–3) rejects valid patients and accepts impossible ones.
- **Response models** fix the shape of what the API returns, so clients can rely on it.

## Step 6: Build the API (app/main.py)

```python
"""Heart disease prediction API with two versions of the contract."""
import os

import joblib
import pandas as pd
from fastapi import FastAPI, Response

from app.schemas import BatchRequestV2, BatchResponseV2, Patient, PredictionV1, PredictionV2

MODEL_PATH = os.environ.get("MODEL_PATH", "models/heart_disease.joblib")

bundle = joblib.load(MODEL_PATH)          # once, at startup
MODEL = bundle["model"]
FEATURES = bundle["features"]
MODEL_VERSION = bundle["version"]

app = FastAPI(title="Heart Disease Prediction API", version="2.0")


def probabilities(patients):
    rows = pd.DataFrame([p.model_dump() for p in patients])[FEATURES]
    return MODEL.predict_proba(rows)[:, 1]


def risk_band(p):
    return "low" if p < 0.3 else "medium" if p < 0.7 else "high"


@app.get("/health")
def health():
    return {"status": "ok", "model_version": MODEL_VERSION}


@app.post("/v1/predict", response_model=PredictionV1)
def predict_v1(patient: Patient, response: Response):
    response.headers["Deprecation"] = "true"
    response.headers["Link"] = '</v2/predict>; rel="successor-version"'
    p = float(probabilities([patient])[0])
    pred = int(p >= 0.5)
    return PredictionV1(prediction=pred, probability=round(p, 4),
                        label="disease" if pred else "no_disease",
                        model_version=MODEL_VERSION)


@app.post("/v2/predict", response_model=BatchResponseV2)
def predict_v2(request: BatchRequestV2):
    probs = probabilities(request.patients)
    return BatchResponseV2(
        results=[PredictionV2(probability=round(float(p), 4), risk=risk_band(p))
                 for p in probs],
        model_version=MODEL_VERSION,
    )
```

What each part does:

- **The model loads once, at startup.** Loading it inside the route would add disk reads and delay to every request for no benefit.
- **`[FEATURES]`** puts the columns in the order the model was trained on, whatever order the client sent the JSON keys in.
- **`/health`** is what a platform (Kubernetes, Cloud Run, SageMaker) polls to decide whether the service is ready for traffic. It also reports which model version is loaded.
- **`/v1/predict`**: one patient in, one 0/1 prediction out. It now carries a `Deprecation: true` header and a `Link` to its successor, telling clients to move to v2.
- **`/v2/predict`**: a **batch** of up to 100 patients in, a probability and a risk band (`low`/`medium`/`high`) for each out. The request and response shapes are different from v1, so this is a **breaking change**, and that is why it lives at a new URL.

### Two version numbers, on purpose

| | Model version (`1.0.0`) | API version (`/v1/`, `/v2/`) |
| --- | --- | --- |
| Changes when | The model is retrained | The request or response **shape** changes |
| Do clients notice? | No: same request, same response shape | Yes: they must change their code |
| Example | Retrain on new data → `1.0.1` | Add a required field, rename a key → `/v2/` |

Mixing the two up causes one of two problems: a routine retrain forces every client to change URLs, or a real breaking change is hidden behind a version string nobody reads.

**What goes wrong without versioning:** suppose a retrain adds a 14th required feature and you edit `Patient` in place. Every existing client that does not send it starts getting `422` on every request, all at once, at deploy time. Making the field optional is not the fix either: some requests would then silently skip a feature the model needs. The fix is a new version, a deprecation notice on the old one, and a date to retire it.

## Step 7: Write the tests (tests/test\_api.py)

`TestClient` runs the app in-process, with no server and no open port. It is fast, and it is what a CI pipeline (Session 10) runs on every push.

```python
from fastapi.testclient import TestClient

from app.main import app

client = TestClient(app)

# Patient 1 of the dataset: 63-year-old man, no heart disease on record.
PATIENT = {
    "age": 63, "sex": 1, "cp": 1, "trestbps": 145, "chol": 233, "fbs": 1,
    "restecg": 2, "thalach": 150, "exang": 0, "oldpeak": 2.3, "slope": 3,
    "ca": 0, "thal": 6,
}


def test_health():
    resp = client.get("/health")
    assert resp.status_code == 200
    assert resp.json() == {"status": "ok", "model_version": "1.0.0"}


def test_v1_predicts_one_patient():
    resp = client.post("/v1/predict", json=PATIENT)
    assert resp.status_code == 200
    body = resp.json()
    assert body["prediction"] in (0, 1)
    assert 0 <= body["probability"] <= 1
    assert body["label"] in ("disease", "no_disease")


def test_v1_is_marked_deprecated():
    resp = client.post("/v1/predict", json=PATIENT)
    assert resp.headers["Deprecation"] == "true"


def test_out_of_range_values_are_rejected_with_422():
    bad = dict(PATIENT, age=-5, sex=2)
    resp = client.post("/v1/predict", json=bad)
    assert resp.status_code == 422
    bad_fields = {err["loc"][-1] for err in resp.json()["detail"]}
    assert bad_fields == {"age", "sex"}


def test_missing_field_is_rejected_with_422():
    incomplete = {k: v for k, v in PATIENT.items() if k != "chol"}
    resp = client.post("/v1/predict", json=incomplete)
    assert resp.status_code == 422


def test_v2_predicts_a_batch():
    older = dict(PATIENT, age=70, cp=4, exang=1, ca=3, thal=7)
    resp = client.post("/v2/predict", json={"patients": [PATIENT, older]})
    assert resp.status_code == 200
    results = resp.json()["results"]
    assert len(results) == 2
    assert all(r["risk"] in ("low", "medium", "high") for r in results)


def test_v2_rejects_v1_style_body():
    resp = client.post("/v2/predict", json=PATIENT)
    assert resp.status_code == 422
```

```bash
python -m pytest -v
```

```text
7 passed
```

The last test shows why versioning matters: a v1 client that sends its usual body to v2 gets a `422`. That is exactly the breakage you avoid by keeping v1 running while clients migrate.

## Step 8: Run the API and call it

```bash
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

Open `http://localhost:8000/docs`. FastAPI builds this interactive page from your Pydantic models, so the documentation always matches the real validation rules. Click **POST /v1/predict → Try it out** to send a request from the browser.

In a **second terminal**:

### A valid v1 request

```bash
curl -i -X POST localhost:8000/v1/predict \
  -H "Content-Type: application/json" \
  -d '{"age":63,"sex":1,"cp":1,"trestbps":145,"chol":233,"fbs":1,"restecg":2,"thalach":150,"exang":0,"oldpeak":2.3,"slope":3,"ca":0,"thal":6}'
```

```text
HTTP/1.1 200 OK
content-type: application/json
deprecation: true
link: </v2/predict>; rel="successor-version"

{"prediction":0,"probability":0.3226,"label":"no_disease","model_version":"1.0.0"}
```

This patient has no heart disease in the records, and the model agrees (probability 0.32). `-i` shows the headers, including the deprecation notice.

### An invalid request

```bash
curl -X POST localhost:8000/v1/predict \
  -H "Content-Type: application/json" \
  -d '{"age":-5,"sex":2,"cp":1,"trestbps":145,"chol":233,"fbs":1,"restecg":2,"thalach":150,"exang":0,"oldpeak":2.3,"slope":3,"ca":0,"thal":6}'
```

```json
{"detail":[
  {"type":"greater_than_equal","loc":["body","age"],"msg":"Input should be greater than or equal to 18","input":-5,"ctx":{"ge":18}},
  {"type":"literal_error","loc":["body","sex"],"msg":"Input should be 0 or 1","input":2,"ctx":{"expected":"0 or 1"}}
]}
```

Status `422`, not `500`. The request never reached the model: Pydantic rejected it while reading the body, and named each bad field and the rule it broke. A client can act on that; a `500` tells it nothing.

### A v2 batch request

```bash
curl -X POST localhost:8000/v2/predict \
  -H "Content-Type: application/json" \
  -d '{"patients":[
        {"age":63,"sex":1,"cp":1,"trestbps":145,"chol":233,"fbs":1,"restecg":2,"thalach":150,"exang":0,"oldpeak":2.3,"slope":3,"ca":0,"thal":6},
        {"age":70,"sex":1,"cp":4,"trestbps":145,"chol":233,"fbs":1,"restecg":2,"thalach":150,"exang":1,"oldpeak":2.3,"slope":3,"ca":3,"thal":7}]}'
```

```json
{"results":[{"probability":0.3226,"risk":"medium"},{"probability":0.893,"risk":"high"}],"model_version":"1.0.0"}
```

The second patient is older, has exercise-induced angina, 3 blocked vessels and a reversible defect, and is rated `high` risk.

## Common errors and fixes

| Error | Cause | Fix |
| --- | --- | --- |
| `FileNotFoundError: models/heart_disease.joblib` | Model not trained, or uvicorn started from another folder | `python -m src.train`; start uvicorn from the project root |
| `ModuleNotFoundError: No module named 'app'` | Ran pytest or uvicorn from inside `app/` | Run from the project root; keep `pytest.ini` |
| `RuntimeError: The starlette.testclient module requires the httpx package` | httpx not installed | `pip install -r requirements.txt` |
| `422` on a request you believe is valid | A coded field uses a value outside its `Literal` (e.g. `cp: 0`) | Check the field in `/docs`; the dataset codes `cp` as 1–4 |
| `422` with `"loc":["body","patients"]` on v2 | Sent a single patient instead of `{"patients": [...]}` | Wrap patients in a list under `patients` |
| `KeyError` on a column name in `probabilities` | Schema field names differ from training columns | Field names in `Patient` must match the dataset's column names |
| `Address already in use` | Another server is on port 8000 | Stop it, or use `--port 8001` |
