# MLOps Pipeline for Real-Time Fraud Detection

## Overview

You will build the parts a real-time risk-scoring system needs: training that copes with class imbalance, a decision band (approve / review / decline) chosen from the **cost** of each mistake, a single-row scoring path fast enough for a request handler, and drift monitoring that works while the true outcomes are still weeks away.

By the end, you will be able to:

- Price both kinds of mistake and compare the model with "do nothing" policies.
- Split data past → future and choose thresholds on validation data only.
- Build an approve / review / decline band and see what it means for staff workload.
- Make single-row scoring fast, and safe under concurrent requests.
- Monitor inputs and decision-band shares with a drift baseline frozen into the model bundle.

**Prerequisites:** Python 3.11 and Sessions 5, 21 and 24. Everything runs locally.

### A note on the data

**This lab does not use a fraud dataset, and does not pretend to.** The UCI repository has no labelled transaction-fraud dataset; the well-known Kaggle credit-card fraud set is not from UCI, and its features are anonymised. Instead we use **[UCI Default of Credit Card Clients](https://archive.ics.uci.edu/dataset/350/default+of+credit+card+clients)**: 30,000 card holders of a Taiwanese bank in 2005, with credit limit, demographics, six months of repayment status, bills and payments, and whether they defaulted the next month. It is downloaded automatically by the code.

Fraud detection and default prediction are different business problems but the **same engineering problem**:

| Property | Real-time fraud | This dataset |
| --- | --- | --- |
| Class imbalance | ~0.1–2% fraud | ~22% default (milder) |
| Unequal error costs | Missed fraud ≫ blocked customer | Missed default ≫ extra review |
| Output is a decision | Approve / review / decline | Approve / review / decline |
| Labels arrive late | Chargebacks: 30–90 days | Default: one billing cycle or more |
| Inputs shift over time | Attackers adapt | The economy changes |

What the stand-in does **not** capture: fraud is **adversarial** (people probe the model and change behaviour, so drift arrives as sudden jumps), fraud imbalance is far more extreme, and the best fraud features are behavioural (transactions per hour, distance from the last purchase, a new device). Treat every **technique** here as transferable and every **number** as belonging to credit default.

## Step 3: Load and split past → future (src/data.py)

```python
"""Load UCI Default of Credit Card Clients with real column names; split by position."""


def load():
    from ucimlrepo import fetch_ucirepo

    ds = fetch_ucirepo(id=350)
    names = ds.variables.set_index("name")["description"]        # X1 -> LIMIT_BAL, ...
    X = ds.data.features.rename(columns=names.to_dict())
    y = ds.data.targets.iloc[:, 0].rename("default")
    return X, y


def split(X, y):
    """First 64% train, next 16% validation, last 20% test: past -> future, never shuffled."""
    a, b = int(len(X) * 0.64), int(len(X) * 0.80)
    return (X.iloc[:a], X.iloc[a:b], X.iloc[b:]), (y.iloc[:a], y.iloc[a:b], y.iloc[b:])
```

- **Real column names from the dataset's own metadata.** UCI ships `X1` … `X23`. A drift alert on `X6` means nothing to the analyst who must act on it; on `PAY_0` it does. Taking the names from `ds.variables` avoids guessing: the repayment columns are `PAY_0, PAY_2, …, PAY_6` (there is no `PAY_1`), which positional renaming gets wrong.
- **`PAY_0`** is last month's repayment status: −2 no use, −1 paid in full, 0 revolving credit, 1–8 months late. Negative values are valid, and so are negative bills (`BILL_AMT1` down to −165,580: account credit). Input validation that rejects negatives would reject real customers.
- **A positional split, not a shuffled one.** In production you train on the past and score the future. There is no timestamp column, so row order is the closest stand-in. We deliberately do **not** stratify: if the default rate differs between periods, you want to see it, not hide it.

| Part | Rows | Used for |
| --- | --- | --- |
| train | 19,200 | Fitting the model |
| validation | 4,800 | Choosing the model and the thresholds |
| test | 6,000 | One honest final check |

## Step 4: Price the mistakes, train, choose the band (src/train.py)

```python
"""Train, choose the decision band from costs on VALIDATION data, check on test, save a bundle."""
from datetime import datetime, timezone

import joblib
import numpy as np
from sklearn.ensemble import HistGradientBoostingClassifier
from sklearn.metrics import average_precision_score, confusion_matrix, roc_auc_score
from sklearn.utils.class_weight import compute_sample_weight

from src.data import load, split

COST_FN = 500.0      # a missed default (or missed fraud)
COST_FP = 60.0       # an unnecessary manual review
MONITORED = ["LIMIT_BAL", "AGE", "PAY_0", "BILL_AMT1", "PAY_AMT1"]

X, y = load()
(X_tr, X_va, X_te), (y_tr, y_va, y_te) = split(X, y)
print(f"rows train/val/test: {len(X_tr)}/{len(X_va)}/{len(X_te)}   default rate "
      f"{y_tr.mean():.3f}/{y_va.mean():.3f}/{y_te.mean():.3f}")
print(f"cost ratio {COST_FN / COST_FP:.1f}:1, break-even probability "
      f"{COST_FP / (COST_FP + COST_FN):.3f}")

common = dict(max_iter=300, learning_rate=0.06, max_leaf_nodes=31, early_stopping=True,
              validation_fraction=0.15, random_state=7)
# Fit on plain arrays: the scoring service sends arrays, not DataFrames.
plain = HistGradientBoostingClassifier(**common).fit(X_tr.to_numpy(), y_tr)
weighted = HistGradientBoostingClassifier(**common).fit(
    X_tr.to_numpy(), y_tr, sample_weight=compute_sample_weight("balanced", y_tr))

pp = plain.predict_proba(X_va.to_numpy())[:, 1]
pw = weighted.predict_proba(X_va.to_numpy())[:, 1]
print(f"\n{'validation':<18}{'plain':>9}{'weighted':>10}")
for name, fn in [("accuracy @0.5", lambda p: ((p > 0.5) == y_va).mean()),
                 ("ROC AUC", lambda p: roc_auc_score(y_va, p)),
                 ("PR AUC", lambda p: average_precision_score(y_va, p))]:
    print(f"{name:<18}{fn(pp):>9.4f}{fn(pw):>10.4f}")
print(f"PR AUC of random guessing: {y_va.mean():.4f}")
# Keep whichever ranks risk better; the threshold below adapts to its probabilities.
model = weighted if average_precision_score(y_va, pw) > average_precision_score(y_va, pp) else plain
print(f"using the {'weighted' if model is weighted else 'plain'} model")


def cost(y_true, p, t):
    tn, fp, fn, tp = confusion_matrix(y_true, p >= t).ravel()
    return fn * COST_FN + fp * COST_FP


# The review threshold comes from VALIDATION data only.
p_va = model.predict_proba(X_va.to_numpy())[:, 1]
grid = np.round(np.arange(0.05, 0.91, 0.05), 2)
costs = {t: cost(y_va, p_va, t) for t in grid}
t_review = min(costs, key=costs.get)
print("\nvalidation cost by threshold:")
for t in [0.05, 0.10, 0.15, 0.20, 0.30, 0.50]:
    print(f"  {t:.2f}  {costs[t]:>9,.0f}  ({costs[t] / costs[t_review] - 1:+.1%} vs best)")
print(f"chosen review threshold: {t_review}")

# Final check on the untouched test set, against the do-nothing policies.
p_te = model.predict_proba(X_te.to_numpy())[:, 1]
print(f"\ntest cost  model @{t_review}: {cost(y_te, p_te, t_review):>9,.0f}")
print(f"test cost  model @0.50: {cost(y_te, p_te, 0.5):>9,.0f}")
print(f"test cost  approve everyone: {y_te.sum() * COST_FN:>9,.0f}")
print(f"test cost  review everyone : {(1 - y_te).sum() * COST_FP:>9,.0f}")

# Decline automatically only where validation precision reaches 75% (confidently bad).
t_decline = float(min(t for t in grid if t > t_review and
                      y_va[p_va >= t].mean() >= 0.75))
print(f"decline threshold (75% precision on validation): {t_decline}")
bands = {"approve": float((p_te < t_review).mean()),
         "review": float(((p_te >= t_review) & (p_te < t_decline)).mean()),
         "decline": float((p_te >= t_decline).mean())}
print("test traffic:", {k: f"{v:.1%}" for k, v in bands.items()})

# Drift baseline: bin edges from training data, and the training share in each bin.
edges, reference = {}, {}
for f in MONITORED:
    e = np.unique(np.quantile(X_tr[f], np.linspace(0, 1, 11)))
    e[0], e[-1] = -np.inf, np.inf
    edges[f] = e.tolist()
    reference[f] = (np.histogram(X_tr[f], e)[0] / len(X_tr)).tolist()
joblib.dump({
    "model": model, "features": X_tr.columns.tolist(),
    "t_review": float(t_review), "t_decline": t_decline,
    "cost_matrix": {"fn": COST_FN, "fp": COST_FP},
    "psi_edges": edges, "psi_reference": reference,      # frozen with the model
    "band_shares": bands,
    "version": "risk-hgb-1",
    "trained_at": datetime.now(timezone.utc).isoformat(timespec="seconds"),
}, "model/risk_model.joblib")
X_te.to_csv("model/test_window.csv", index=False)
print("saved model/risk_model.joblib")
```

### 1. The costs, before any model

```text
rows train/val/test: 19200/4800/6000   default rate 0.230/0.199/0.211
cost ratio 8.3:1, break-even probability 0.107
```

A missed default costs 500; an unnecessary review costs 60. **Write these down before training.** The default threshold of 0.5 is only right when both mistakes cost the same, which in risk work is essentially never. The break-even probability (60 / (60 + 500) = 0.107) is where reviewing and approving have the same expected cost, for a perfectly calibrated model.

The default rate moves between periods (23.0% → 19.9% → 21.1%). A stratified split would have hidden that.

### 2. Class weighting

```text
validation            plain  weighted
accuracy @0.5        0.8433    0.7829
ROC AUC              0.7820    0.7858
PR AUC               0.5430    0.5522
PR AUC of random guessing: 0.1994
using the weighted model
```

- **Accuracy is misleading here**: answering "no default" for everyone is ~80% accurate.
- **Weighting made accuracy worse and ranking slightly better.** `class_weight`-style weighting mostly moves where 0.5 falls; it changes the model's ability to **rank** customers (ROC AUC, PR AUC) only a little. Since the threshold is chosen from costs next, ranking is what matters; the script keeps whichever model has the higher PR AUC.
- **PR AUC 0.55 against 0.20 for random guessing**: a useful model, nearly 3× better than chance at the precision/recall trade-off.
- Weighting is preferred over oversampling (e.g. SMOTE): it adds no synthetic rows and cannot leak. At 0.1% fraud, oversampling becomes worth testing.

### 3. The threshold, from costs on validation

```text
validation cost by threshold:
  0.05    230,580  (+23.1% vs best)
  0.10    228,200  (+21.8% vs best)
  0.15    216,480  (+15.6% vs best)
  0.20    200,460  (+7.0% vs best)
  0.30    188,400  (+0.6% vs best)
  0.50    244,240  (+30.4% vs best)
chosen review threshold: 0.25
```

The cheapest threshold is **0.25**, not 0.5 and not the theoretical 0.107. Weighting pushed this model's probabilities **up**, so its best cut-off is higher than for the plain model. **A threshold belongs to one specific model**: a retrained or reweighted model needs its thresholds re-derived, which is why they are saved in the bundle. The curve is flat between 0.25 and 0.30, so don't treat 0.25 as precise.

### 4. The honest final check, against do-nothing policies

```text
test cost  model @0.25:   231,340
test cost  model @0.50:   300,060
test cost  approve everyone:   633,000
test cost  review everyone :   284,040
```

- The cost-chosen threshold saves **23%** against the default 0.5, with no new data and no retraining: often the highest-return hour of work in a risk pipeline.
- **Always compare with the trivial policies.** Reviewing every application costs 284,040. A model that cannot beat that is worse than no model; this one does (231,340), by 19%. With cheaper reviews or a different default rate, it might not, and you must say so when it does not.

### 5. The decision band, and what it means for staff

```text
decline threshold (75% precision on validation): 0.85
test traffic: {'approve': '26.6%', 'review': '66.1%', 'decline': '7.3%'}
```

Three bands: below 0.25 approve automatically, 0.25–0.85 send to a person, from 0.85 decline automatically (where at least 75% of validation cases really defaulted).

**Two thirds of all applications go to manual review.** The cost model assumed reviewing is always possible at 60 per case; no operations team can absorb 66% of traffic. In practice the review **capacity** is fixed, and the threshold is set to fill it. The cost curve then tells you what that staffing decision costs, which turns "the model is too cautious" into a conversation about how many analysts a given loss rate is worth. Put these three percentages in front of the operations lead, not the AUC.

## Step 5: The hot path (serving/score.py)

```python
"""Single-row scoring for a request handler: no pandas on the hot path."""
import threading

import joblib
import numpy as np
from threadpoolctl import threadpool_limits

BUNDLE = joblib.load("model/risk_model.joblib")
MODEL, FEATURES = BUNDLE["model"], BUNDLE["features"]
T_REVIEW, T_DECLINE = BUNDLE["t_review"], BUNDLE["t_decline"]
_local = threading.local()

# One row is tiny work; starting OpenMP threads for it costs more than the work itself.
threadpool_limits(limits=1, user_api="openmp")


def _buffer():
    # One reusable array per thread: shared across threads, concurrent requests would mix rows.
    if not hasattr(_local, "buf"):
        _local.buf = np.empty((1, len(FEATURES)), dtype=np.float64)
    return _local.buf


def score(record):
    buf = _buffer()
    for j, name in enumerate(FEATURES):
        buf[0, j] = record[name]
    p = float(MODEL.predict_proba(buf)[0, 1])
    decision = "decline" if p >= T_DECLINE else "review" if p >= T_REVIEW else "approve"
    return {"risk": round(p, 4), "decision": decision, "model_version": BUNDLE["version"]}
```

- **Thresholds come from the bundle**, never from a config file next to it. Shipping a retrained model with last quarter's thresholds silently changes the bank's risk policy, and no deployment log would show it.
- **A reusable buffer per thread** avoids allocating an array per request. A single shared buffer would let two concurrent requests overwrite each other's values and score a mixture of both customers: plausible wrong answers that only appear under load. `threading.local()` gives each thread its own.
- **`threadpool_limits(1)`**: see Step 6.

### tests/test\_score.py

```python
from concurrent.futures import ThreadPoolExecutor

import pandas as pd

from serving.score import FEATURES, MODEL, T_DECLINE, T_REVIEW, score

ROWS = pd.read_csv("model/test_window.csv").head(200)


def test_fast_path_matches_the_model():
    expected = MODEL.predict_proba(ROWS[FEATURES].to_numpy())[:, 1]
    got = [score(r)["risk"] for r in ROWS.to_dict(orient="records")]
    assert max(abs(a - b) for a, b in zip(expected, got)) < 1e-4


def test_decision_follows_the_band():
    for r in ROWS.to_dict(orient="records"):
        out = score(r)
        expect = ("decline" if out["risk"] >= T_DECLINE
                  else "review" if out["risk"] >= T_REVIEW else "approve")
        assert out["decision"] == expect


def test_concurrent_requests_do_not_mix_rows():
    records = ROWS.to_dict(orient="records")
    serial = [score(r)["risk"] for r in records]
    with ThreadPoolExecutor(max_workers=8) as pool:
        parallel = list(pool.map(lambda r: score(r)["risk"], records))
    assert parallel == serial
```

## Step 6: Measure the latency (src/latency.py)

```python
"""Pandas vs plain-array scoring for ONE record: same answer, very different latency."""
import time

import numpy as np
import pandas as pd

from serving.score import FEATURES, MODEL, score

record = pd.read_csv("model/test_window.csv").iloc[0].to_dict()


def score_with_pandas(rec):
    return float(MODEL.predict_proba(pd.DataFrame([rec])[FEATURES].to_numpy())[0, 1])


assert abs(score_with_pandas(record) - score(record)["risk"]) < 1e-4   # same function


def bench(fn, n=2000):
    fn(record)
    lat = []
    for _ in range(n):
        t0 = time.perf_counter()
        fn(record)
        lat.append((time.perf_counter() - t0) * 1000)
    return np.percentile(lat, [50, 99])


for name, fn in [("pandas row", score_with_pandas), ("numpy row", score)]:
    p50, p99 = bench(fn)
    print(f"{name:<11} p50 {p50:.3f} ms   p99 {p99:.3f} ms")
```

When building this lab, the first version **did not** limit threads, and measured:

```text
pandas row  p50 2.622 ms   p99 5.264 ms
numpy row   p50 1.991 ms   p99 4.608 ms
```

The DataFrame was **not** the main cost. `HistGradientBoostingClassifier` uses OpenMP threads for prediction (8 on this machine); for one row, starting those threads costs far more than the arithmetic. Limiting the scoring process to one thread made the numpy path **5.6× faster at p50 and 12× faster at p99**. Dropping pandas then halves what is left. (Session 21 found the same with a random forest's `n_jobs`.) Your numbers depend on your computer; the ratios are what matter.

Read the **p99**, not the average: a payment gateway times out on the slow tail. Under 0.4 ms leaves plenty of room in a typical 10 ms budget for network, feature lookup and logging. Measure before optimising: the obvious suspect (pandas) was not the biggest cost.

## Step 7: Monitor before the labels arrive (src/monitor.py)

A default is confirmed a billing cycle later; a fraud chargeback 30–90 days later. By the time an accuracy dashboard turns red, you have been scoring badly for weeks. So watch the **inputs** and the **decisions**, continuously.

```python
"""Drift report for a window of applications, using the frozen baseline in the bundle.

Usage: python -m src.monitor stable | downturn
"""
import sys

import numpy as np
import pandas as pd

from serving.score import BUNDLE, MODEL, T_DECLINE, T_REVIEW


def psi(feature, values):
    edges = np.array(BUNDLE["psi_edges"][feature])
    ref = np.clip(np.array(BUNDLE["psi_reference"][feature]), 1e-6, None)
    cur = np.clip(np.histogram(values, edges)[0] / len(values), 1e-6, None)
    return float(((cur - ref) * np.log(cur / ref)).sum())


window = pd.read_csv("model/test_window.csv")
if sys.argv[1] == "stable":
    window = window.iloc[:2000]
else:                                    # a downturn: payments slip, limits are cut
    rng = np.random.default_rng(11)
    window = window.iloc[2000:4000].copy()
    window["PAY_0"] = np.clip(window["PAY_0"] + rng.poisson(0.8, len(window)), -2, 8)
    window["LIMIT_BAL"] = window["LIMIT_BAL"] * rng.uniform(0.55, 0.85, len(window))

print(f"{'feature':<11}{'PSI':>8}  status")
for f in BUNDLE["psi_edges"]:
    v = psi(f, window[f])
    print(f"{f:<11}{v:>8.3f}  {'OK' if v < 0.10 else 'WATCH' if v < 0.25 else 'ALERT'}")

p = MODEL.predict_proba(window[BUNDLE["features"]].to_numpy())[:, 1]
now = {"approve": (p < T_REVIEW).mean(), "review": ((p >= T_REVIEW) & (p < T_DECLINE)).mean(),
       "decline": (p >= T_DECLINE).mean()}
print("\ndecision band   baseline   this window")
for band, share in now.items():
    print(f"{band:<14}{BUNDLE['band_shares'][band]:>9.1%}{share:>13.1%}")
```

**The PSI bin edges and reference shares are frozen in the bundle.** Recomputing the edges from each new window compares the window with itself, and PSI stays near zero whatever happens: a monitor that cannot alert, yet is trusted.

- **PSI points at the columns that moved**: the two we shifted alert; the rest stay at the noise floor. Two related features moving together (later payments **and** lower limits) is a coherent economic story. One feature jumping alone while everything else is perfectly still is far more often a **broken upstream feed** (amounts suddenly in different units, a recoded category) than a changed population. In that case fix the pipeline; do **not** retrain on corrupted inputs.
- **The decision bands show the operational impact the same day**: automatic approvals halve, declines double, and the review queue, already the bottleneck, grows. The queue depth is often the first alarm anyone notices, long before accuracy can be measured.
- **Watch band shares even when PSI is calm.** PSI checks one feature at a time; it cannot see a change in how features relate to the outcome, or a slow drift in the model's own scores. Shares creeping over weeks mean the same threshold now means something different. Re-derive thresholds on recent labelled data on a schedule, independently of retraining.

## What the stand-in leaves out

Before carrying this design to real fraud:

- **Adversaries.** Fraudsters probe for your boundary. Expect sudden step changes within hours, so check drift hourly, not daily, and watch the score distribution itself.
- **Extreme imbalance.** At 0.5% fraud, PR AUC is much noisier, one validation set is not enough to fit a threshold, and oversampling becomes worth testing.
- **Behavioural features.** Velocity and device features need a low-latency feature store lookup inside the request budget, and it is usually slower than the model.
- **Censored labels.** You only learn the outcome of transactions you **approved**. Declined ones never get a label, so training data is a biased sample of your own past decisions.

## Common errors and fixes

| Error | Cause | Fix |
| --- | --- | --- |
| Column names `X1` … `X23` | Raw UCI names | Rename from `ds.variables`, as in `load()` |
| A `PAY_1` column, and repayment columns shifted by one | Renamed by position | The real names are `PAY_0, PAY_2, …, PAY_6` |
| Model looks great, disappoints in production | Shuffled split or thresholds chosen on test data | Split past → future; choose thresholds on validation |
| `UserWarning: X does not have valid feature names` | Fitted on a DataFrame, scored with arrays | Fit on `.to_numpy()`, as the service sends arrays |
| Single-row latency of several ms | OpenMP threads started for every prediction | `threadpool_limits(limits=1, user_api="openmp")` in the scorer |
| Wrong scores only under load | One buffer shared between threads | `threading.local()` buffers |
| PSI always near zero | Bin edges recomputed from the current window | Freeze edges and reference shares in the bundle |
| One feature's PSI > 1 overnight | Usually a units or encoding change upstream | Check min/max and types against training; fix the feed, don't retrain |
