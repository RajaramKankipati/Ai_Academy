# Real-Time IoT Predictive Maintenance using MLOps

## Overview

You will build the streaming half of an MLOps system: telemetry from milling machines arrives one reading at a time, a model scores each reading for failure risk, an alert rule decides when to call a technician, and two monitoring panels track **latency** and **flag-rate drift**.

Real-time scoring changes the problems you worry about:

- **You do not control the arrival rate.** If scoring takes longer than the gap between readings, a queue builds up. Nothing errors; the predictions just get later and later.
- **Latency is part of correctness.** A failure warning that arrives after the machine has stopped is a log entry, not a prediction. Watch the slowest readings (p99), not the average.
- **Alerts have their own cost.** Too many and technicians stop reading them.
- **Labels arrive late.** "Did it really fail?" comes from the maintenance log hours later, so live monitoring watches the share of **flagged** readings.

By the end, you will be able to:

- Keep feature engineering in **one** function used by both training and the stream.
- Choose an alert threshold from the costs of false alarms and missed failures.
- Score a simulated stream and report throughput, latency and flag rate.
- Recognise when an alert rule assumes a data structure your data does not have.
- Speed up a lagging consumer with batching and single-threaded scoring.

**Prerequisites:** Python 3.11. Everything runs locally.

**Dataset:** [UCI AI4I 2020 Predictive Maintenance](https://archive.ics.uci.edu/dataset/601/ai4i+2020+predictive+maintenance+dataset), 10,000 synthetic but realistic milling-machine readings: air and process temperature, rotational speed, torque, tool wear and product quality type (L/M/H), with a `Machine failure` label and five failure-mode flags. Each row is one product being machined. It is downloaded automatically by the code.

## Step 3: One feature function (src/features.py)

```python
"""One feature function, shared by training and the streaming scorer."""
import math

TYPE_CODES = {"L": 0, "M": 1, "H": 2}
FEATURES = ["air_temperature", "process_temperature", "rotational_speed", "torque",
            "tool_wear", "type_code", "power_w", "temp_delta_k", "wear_torque"]


def features(msg):
    """msg: one sensor reading as a dict with the device's field names."""
    torque, speed = msg["torque"], msg["rotational_speed"]
    return [
        msg["air_temperature"], msg["process_temperature"], speed, torque, msg["tool_wear"],
        TYPE_CODES[msg["type"]],
        torque * speed * 2 * math.pi / 60,                    # mechanical power, W
        msg["process_temperature"] - msg["air_temperature"],  # heat not dissipated, K
        msg["tool_wear"] * torque,                            # cumulative stress
    ]
```

- **Derived physics features.** Power (torque × angular speed), the temperature difference (heat not carried away) and wear × torque (accumulated stress) are what actually drive failures. Computing them saves the model from rediscovering physics from 10,000 mostly uneventful rows.
- **One function for training and serving.** If training computed features in pandas and the stream computed them separately, a small difference (a missing `2π/60`) would give the model different numbers in production, with no error: **training/serving skew**. Here both call `features()` on the same message format.

## Step 4: Train and choose the alert threshold (src/train.py)

```python
"""Train the failure-risk model, choose the alert threshold from costs, save one bundle."""
import joblib
import numpy as np
from sklearn.ensemble import RandomForestClassifier
from sklearn.metrics import average_precision_score, roc_auc_score
from sklearn.model_selection import cross_val_predict, train_test_split

from src.data import FAILURE_MODES, load_readings
from src.features import FEATURES, features

COST_FALSE_ALARM = 250      # an unnecessary inspection
COST_MISSED_FAILURE = 8000  # an unplanned stoppage

df = load_readings()
print(f"{len(df)} readings, failure rate {df['failure'].mean():.2%}")
print("failure modes:", {m: int(df[m].sum()) for m in FAILURE_MODES})

# The mode flags are recorded AFTER a failure, so they are never model inputs.
X = np.array([features(r) for r in df.to_dict(orient="records")])
y = df["failure"].values
idx_tr, idx_te = train_test_split(np.arange(len(df)), test_size=0.25, random_state=42,
                                  stratify=y)
X_tr, X_te, y_tr, y_te = X[idx_tr], X[idx_te], y[idx_tr], y[idx_te]

model = RandomForestClassifier(n_estimators=120, max_depth=12, min_samples_leaf=3,
                               class_weight="balanced_subsample", n_jobs=-1, random_state=42)

# Threshold from cross-validated scores on the TRAINING data.
cv = cross_val_predict(model, X_tr, y_tr, cv=5, method="predict_proba")[:, 1]
print(f"\n{'threshold':>9} {'alerts':>7} {'caught':>7} {'missed':>7} {'cost per 1k':>12}")
best = None
for t in [0.70, 0.50, 0.35, 0.25, 0.15, 0.10, 0.08, 0.05, 0.03]:
    alerts, caught = int((cv >= t).sum()), int(((cv >= t) & (y_tr == 1)).sum())
    missed = int(y_tr.sum()) - caught
    cost = ((alerts - caught) * COST_FALSE_ALARM + missed * COST_MISSED_FAILURE) / len(y_tr) * 1000
    print(f"{t:>9.2f} {alerts:>7} {caught:>7} {missed:>7} {cost:>12,.0f}")
    if best is None or cost < best[1]:
        best = (t, cost)
threshold = best[0]
print(f"chosen threshold: {threshold}")

model.fit(X_tr, y_tr)
p = model.predict_proba(X_te)[:, 1]
print(f"\ntest ROC AUC {roc_auc_score(y_te, p):.4f}   average precision "
      f"{average_precision_score(y_te, p):.4f}")
print(f"test at threshold {threshold}: {int((p >= threshold).sum())} alerts, "
      f"{int(((p >= threshold) & (y_te == 1)).sum())} of {int(y_te.sum())} failures caught")
ranked = sorted(zip(FEATURES, model.feature_importances_), key=lambda kv: -kv[1])[:4]
print("top features:", ", ".join(f"{f} {i:.3f}" for f, i in ranked))

model.n_jobs = 1   # threads speed up training but slow down one-reading-at-a-time scoring
joblib.dump({"model": model, "threshold": threshold,
             "baseline_flag_rate": float((p >= threshold).mean())},
            "model/bundle.joblib")
df.iloc[idx_te].to_csv("model/test_readings.csv", index=False)     # the stream we replay
print("saved model/bundle.joblib and model/test_readings.csv")
```

How to read it:

- **The five failure-mode flags are never inputs.** They are filled in **after** a failure (which kind it was). As features they would score perfectly in training and be useless live, where they do not exist yet: textbook leakage.
- **`RNF` (19 cases) is the random failure mode.** By design no sensor predicts it, so no honest model catches 100% of failures.
- **Quote average precision, not just AUC.** With 3.4% failures, AUC (0.976) is flattered by the huge "no failure" class. Average precision (0.868) reflects the trade-off you will live with when alerting.
- **The threshold comes from money.** A missed failure costs 32 times an unnecessary inspection, so the cheapest threshold is far below 0.5. The curve is flat between 0.15 and 0.05, so do not over-tune: any value there is reasonable. The threshold was chosen on cross-validated **training** scores and then confirmed on test (80 of 85 caught).
- **`model.n_jobs = 1` before saving.** Parallel threads speed up training, but for one reading at a time, starting threads costs more than the work: scoring one reading took **15 ms with `n_jobs=-1` and 2 ms with `n_jobs=1`**. That single line is a 7× latency improvement.
- **The bundle** carries the model, threshold and baseline flag rate together. A retrain moves both numbers; a consumer that read the threshold from an environment variable would keep alerting at the old value without anyone noticing.

## Step 5: The scorer (src/scorer.py)

```python
"""Score one reading at a time and decide whether it raises an alert."""
import time
from collections import defaultdict, deque

from src.features import features


class StreamScorer:
    def __init__(self, model, threshold, consecutive_required=1):
        self.model = model
        self.threshold = threshold
        self.consecutive_required = consecutive_required   # 1 = alert on every high reading
        self.streak = defaultdict(int)
        self.latencies_ms = deque(maxlen=5000)
        self.risks = deque(maxlen=5000)

    def score(self, msg):
        t0 = time.perf_counter()
        risk = float(self.model.predict_proba([features(msg)])[0, 1])
        self.latencies_ms.append((time.perf_counter() - t0) * 1000)
        self.risks.append(risk)

        machine = msg["machine_id"]
        self.streak[machine] = self.streak[machine] + 1 if risk >= self.threshold else 0
        alert = self.streak[machine] >= self.consecutive_required
        return {"machine_id": machine, "risk": round(risk, 4), "alert": alert}
```

- **`latencies_ms` and `risks`** keep the last 5,000 values for the monitoring panels.
- **`consecutive_required`** is a common anti-noise rule: only alert when a machine gives N high readings in a row. Step 7 shows what it does on this data.

### tests/test\_scorer.py

import numpy as np

from src.features import features
from src.scorer import StreamScorer

READING = {"machine_id": "MILL-01", "type": "L", "air_temperature": 298.1,
           "process_temperature": 308.6, "rotational_speed": 1551, "torque": 42.8,
           "tool_wear": 0}


class FixedRisk:                         # a stand-in model that returns a chosen risk
    def __init__(self, risk):
        self.risk = risk

    def predict_proba(self, X):
        return np.array([[1 - self.risk, self.risk]])


def test_features_are_physics():
    v = features(READING)
    assert round(v[6]) == round(42.8 * 1551 * 2 * 3.14159265 / 60)   # power in watts
    assert round(v[7], 1) == 10.5                                     # temperature delta


def test_high_risk_alerts_and_low_risk_does_not():
    assert StreamScorer(FixedRisk(0.9), 0.1).score(READING)["alert"] is True
    assert StreamScorer(FixedRisk(0.05), 0.1).score(READING)["alert"] is False


def test_consecutive_rule_needs_two_high_readings_from_the_same_machine():
    s = StreamScorer(FixedRisk(0.9), 0.1, consecutive_required=2)
    other = dict(READING, machine_id="MILL-02")
    assert [s.score(READING)["alert"], s.score(other)["alert"],

## Step 6: Run the stream (src/stream.py)

In production, readings would arrive through MQTT (AWS IoT Core), Kafka or Kinesis. This script replays 400 held-out readings at a fixed rate, from 8 machines, and prints the monitoring panels at the end.

```python
"""Replay held-out readings as a live stream from 8 machines; score each; report the panels.

Usage: python -m src.stream [hz] [consecutive_required]
"""
import json
import random
import sys
import time

import joblib
import numpy as np
import pandas as pd

from src.scorer import StreamScorer

hz = float(sys.argv[1]) if len(sys.argv) > 1 else 25
consecutive = int(sys.argv[2]) if len(sys.argv) > 2 else 1
bundle = joblib.load("model/bundle.joblib")
scorer = StreamScorer(bundle["model"], bundle["threshold"], consecutive)
readings = pd.read_csv("model/test_readings.csv").sample(400, random_state=7)
rng = random.Random(7)

start, caught, missed, false_alerts = time.time(), 0, 0, 0
for row in readings.to_dict(orient="records"):
    msg = {k: row[k] for k in ["type", "air_temperature", "process_temperature",
                               "rotational_speed", "torque", "tool_wear"]}
    msg["machine_id"] = f"MILL-{rng.randint(1, 8):02d}"
    out = scorer.score(msg)
    if out["alert"]:
        print(f"[ALERT] {out['machine_id']} risk={out['risk']:.3f} truth={row['failure']}")
    caught += out["alert"] and row["failure"]
    missed += (not out["alert"]) and row["failure"]
    false_alerts += out["alert"] and not row["failure"]
    time.sleep(1 / hz)

elapsed = time.time() - start
lat = np.array(scorer.latencies_ms)
flags = np.array(scorer.risks) >= bundle["threshold"]
print(json.dumps({
    "throughput": {"readings": len(readings), "per_second": round(len(readings) / elapsed, 1),
                   "requested_per_second": hz},
    "latency_ms": {"p50": round(float(np.percentile(lat, 50)), 2),
                   "p99": round(float(np.percentile(lat, 99)), 2),
                   "max": round(float(lat.max()), 2)},
    "flag_rate": {"baseline": round(bundle["baseline_flag_rate"], 3),
                  "per_100_readings": [round(float(flags[i:i + 100].mean()), 3)
                                       for i in range(0, len(flags), 100)]},
    "outcome": {"failures_caught": int(caught), "failures_missed": int(missed),
                "false_alerts": int(false_alerts)},
}, indent=2))
```

The message fields are built from the device field names, and the true label (`row["failure"]`) is used **only** to count outcomes at the end, which a live system cannot do until the maintenance log arrives.

| Panel | What it says here |
| --- | --- |
| Throughput | 17.5 readings/s against 25 requested: each reading costs the 40 ms gap **plus** ~8 ms of scoring. Against a real broker, the missing 7.5 readings/s would pile up in a queue, and every prediction would be a little later than the last |
| Latency | p99 under 14 ms, far inside a 40 ms budget per reading. Watch p99 and max, not the average: the slow tail is where late warnings come from |
| Flag rate | 9–12% per 100 readings against a 10% baseline: normal variation. A steady climb across windows would mean the machines, or the sensors, have changed |
| Outcome | 14 of 17 failures caught with 28 false alarms: two inspections per real failure, the trade the 32:1 cost ratio asked for |

## Step 7: An alert rule the data cannot support

"Only alert after two high readings in a row from the same machine" is a popular way to avoid paging on a one-off sensor glitch. Try it:

```bash
python -m src.stream 25 2
```

```json
  "outcome": {"failures_caught": 0, "failures_missed": 17, "false_alerts": 3}
```

**It caught none of the 17 failures.** The rule assumes a failing machine produces a **run** of rising readings over time. In this dataset each row is an independent product being machined; there is no per-machine time series. A high-risk reading is almost never followed by another from the same machine, so the rule suppresses exactly the readings that matter.

Before adding alert logic (consecutive readings, cool-down periods, smoothing), check that your data has the structure the logic assumes. With real per-machine time series it can be the right tool; here it silently turns the alerting off.

## Step 8: Why consumers fall behind, and the fix (src/batching.py)

The most common streaming incident is not a crash: scoring gets slower (a bigger model after a retrain, a busy host) and the consumer starts lagging. Predictions keep coming out, but about the past.

```python
"""Why consumers fall behind: per-call overhead. 50 readings, one call vs 50 calls."""
import time

import joblib
import pandas as pd

from src.features import features

model = joblib.load("model/bundle.joblib")["model"]
rows = pd.read_csv("model/test_readings.csv").head(50).to_dict(orient="records")
vectors = [features(r) for r in rows]
model.predict_proba(vectors[:1])                     # warm up

t0 = time.perf_counter()
model.predict_proba(vectors)
batched = (time.perf_counter() - t0) * 1000

t0 = time.perf_counter()
for v in vectors:
    model.predict_proba([v])
looped = (time.perf_counter() - t0) * 1000

print(f"50 readings, one call : {batched:7.2f} ms ({batched / 50:.2f} ms per reading)")
print(f"50 readings, 50 calls : {looped:7.2f} ms ({looped / 50:.2f} ms per reading)")
print(f"speed-up: {looped / batched:.0f}x")
```

```bash
python -m src.batching
```

```text
50 readings, one call :    2.74 ms (0.05 ms per reading)
50 readings, 50 calls :  109.81 ms (2.20 ms per reading)
speed-up: 40x
```

Almost all the per-reading cost is **fixed overhead per call**, not model computation. The fix for lag is rarely a smaller model; it is **micro-batching**: collect readings for, say, 200 ms (or until 50 arrive) and score them in one call. You add at most 200 ms of delay and gain about 40× throughput, a good trade whenever a warning is useful minutes ahead. Two cautions: flush the buffer on a timer as well as on size, or a quiet machine's reading waits forever; and report latency per **reading**, including the wait in the buffer, not per batch call.

### On real infrastructure

| This lab | AWS | Google Cloud |
| --- | --- | --- |
| `stream.py` replay | IoT Core → Kinesis Data Streams | Pub/Sub (Session 16) |

**In-process vs remote scoring.** Calling a SageMaker endpoint per reading adds 15–40 ms of network time to 0.05 ms of model work. High-rate streams usually load the model **into** the consumer (the bundle is about 1 MB, small enough for a Lambda package) and keep remote endpoints for slower, larger models.

## Common errors and fixes

| Error | Cause | Fix |
| --- | --- | --- |
| Model scores almost perfectly in training | Failure-mode flags (`TWF`, `HDF`, ...) used as features | They are recorded after the failure; never use them as inputs |
| `KeyError: 'Air temperature'` in the stream | Device field names differ from dataset names | Rename once in `load_readings`; use `features()` everywhere |
| Live predictions differ from offline ones | Features computed differently in training and serving | One `features()` function for both |
| Per-reading latency 10+ ms for a small forest | `n_jobs=-1` on single-reading predictions | Set `model.n_jobs = 1` before saving |
| Throughput below the arrival rate | Per-call overhead | Micro-batch: one `predict_proba` per buffer |
| Alerts never fire on real failures | An alert rule assumes a time structure the data lacks | Check the data before adding consecutive/cool-down rules (Step 7) |
| `FileNotFoundError: model/bundle.joblib` | Not trained | `python -m src.train` |
