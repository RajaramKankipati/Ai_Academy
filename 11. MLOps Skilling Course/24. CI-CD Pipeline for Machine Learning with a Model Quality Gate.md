# CI-CD Pipeline for Machine Learning with a Model Quality Gate

## Overview

Session 10 put a quality gate in CI with fixed thresholds. This session adds the rule that does most of the real work: **no regression against the model currently in production**. Every pull request retrains the model; it can merge only if the candidate clears fixed floors **and** is not worse than what is deployed. When a model is promoted, its scores become the new bar, so the bar only ever goes up (a **ratchet**).

Why it matters: a change to feature engineering, a library upgrade or a "harmless" setting can leave every unit test green while making the model worse. Nothing in a normal test suite knows what accuracy **was** yesterday.

| Rule | Example | Stops |
| --- | --- | --- |
| **Floor** | accuracy ≥ 0.88, macro F1 ≥ 0.90 | Something catastrophically broken |
| **No regression** | not more than 0.005 below the deployed model | A model that is "good enough" but worse than what users have now |

By the end, you will be able to:

- Freeze an evaluation set and pin it with a hash, so every model is judged on identical data.
- Write a gate that applies both rules and reports every failure at once.
- Promote a model and raise the bar.
- Wire it into GitHub Actions without the `tee` bug that silently disables the gate.

**Prerequisites:** Python 3.11 and Session 10 (GitHub repository, `gh`, branch protection). Steps 1–8 run locally.

**Dataset:** [UCI Ionosphere](https://archive.ics.uci.edu/dataset/52/ionosphere), 351 radar returns from an antenna array in Goose Bay, Labrador: 34 numeric pulse measurements, labelled `g` (good: shows structure in the ionosphere) or `b` (bad). It retrains in about a second, so the gate can run on every pull request. The features have no human-readable meaning, so a reviewer **cannot** judge a feature change by reading the diff; the gate has to. It is downloaded automatically by the code.

## Step 3: Freeze the evaluation set (prepare\_data.py)

**This is the most important step, and the one most often skipped.** If every CI run did its own `train_test_split`, the candidate and the deployed model would be scored on different rows, and part of any difference would be luck. On 88 test rows, one row is 1.1 accuracy points. A gate that fires at random gets switched off within a week.

So: split **once**, write both files, commit them, and record the holdout's hash.

```python
"""Split the data ONCE and freeze the holdout. Run once; commit data/ to the repo."""
import hashlib

import pandas as pd
from sklearn.model_selection import train_test_split
from ucimlrepo import fetch_ucirepo

ds = fetch_ucirepo(id=52)
X, y = ds.data.features, ds.data.targets["Class"]
print(f"{len(X)} radar returns, {X.shape[1]} features, classes {y.value_counts().to_dict()}")
print(f"constant columns: {[c for c in X.columns if X[c].nunique() == 1]}")

X_tr, X_ho, y_tr, y_ho = train_test_split(X, y, test_size=0.25, random_state=7, stratify=y)
pd.concat([X_tr, y_tr], axis=1).to_csv("data/train.csv", index=False)
pd.concat([X_ho, y_ho], axis=1).to_csv("data/holdout.csv", index=False)
digest = hashlib.sha256(open("data/holdout.csv", "rb").read()).hexdigest()
print(f"train {len(X_tr)} rows, holdout {len(X_ho)} rows {y_ho.value_counts().to_dict()}")
print(f"holdout sha256: {digest[:16]}")
```

```bash
python prepare_data.py
```

```text
351 radar returns, 34 features, classes {'g': 225, 'b': 126}
constant columns: ['Attribute2']
train 263 rows, holdout 88 rows {'g': 56, 'b': 32}
holdout sha256: d8849fe109a3c729
```

- **64% of returns are `g`**, so always answering `g` scores 0.64 accuracy. That is why the floor is 0.88, far above it.
- **`Attribute2` is constant**: it carries no information, and removing it should change nothing. If it did, your pipeline would not be deterministic.
- **The hash** is checked by the gate before it scores anything. If anyone regenerates the holdout, the gate refuses to compare instead of reporting a meaningless difference.

## Step 4: The training script (train.py)

CI cannot run a notebook. Pull requests change the settings at the top of this file.

```python
"""Train the candidate model. Reads data/train.csv, writes models/candidate.joblib."""
import json
import os

import joblib
import pandas as pd
from sklearn.ensemble import RandomForestClassifier

DROP_FEATURES: list[str] = []          # pull requests change these settings
N_ESTIMATORS = 300
MAX_DEPTH = None
EXPECTED_TRAIN_ROWS = 263              # guards against training on the holdout by accident


def main():
    df = pd.read_csv("data/train.csv")
    assert len(df) == EXPECTED_TRAIN_ROWS, f"expected {EXPECTED_TRAIN_ROWS} rows, got {len(df)}"
    y = df["Class"]
    X = df.drop(columns=["Class"] + DROP_FEATURES)
    model = RandomForestClassifier(n_estimators=N_ESTIMATORS, max_depth=MAX_DEPTH,
                                   random_state=0, n_jobs=-1)
    model.fit(X, y)
    os.makedirs("models", exist_ok=True)
    joblib.dump({"model": model, "features": X.columns.tolist()}, "models/candidate.joblib")
    print(json.dumps({"trained_on": len(X), "n_features": X.shape[1],
                      "n_estimators": N_ESTIMATORS}))


if __name__ == "__main__":
    main()
```

- **`random_state=0`.** The gate compares models; if training itself were random, a pull request that changes nothing could still move the numbers.
- **The feature list is saved with the model**, so the gate scores each model on exactly the columns it was trained on, even after a pull request drops some.
- **`EXPECTED_TRAIN_ROWS`**: if someone "fixes" the loader to read the full dataset, training would include the holdout and every model would look great. The hash check catches a **changed** holdout; this assert catches a **leaked** one.

## Step 5: The gate (quality\_gate.py)

```python
"""Block the pull request unless the candidate clears the floor AND does not regress."""
import hashlib
import json
import sys

import joblib
import pandas as pd
from sklearn.metrics import accuracy_score, f1_score

MIN_ACCURACY = 0.88
MIN_MACRO_F1 = 0.90
REGRESSION_TOLERANCE = 0.005


def evaluate(path):
    bundle = joblib.load(path)
    df = pd.read_csv("data/holdout.csv")
    pred = bundle["model"].predict(df[bundle["features"]])
    return {"accuracy": round(float(accuracy_score(df["Class"], pred)), 4),
            "macro_f1": round(float(f1_score(df["Class"], pred, average="macro")), 4)}


def main():
    deployed = json.load(open("deployed_metrics.json"))
    digest = hashlib.sha256(open("data/holdout.csv", "rb").read()).hexdigest()
    if not digest.startswith(deployed["holdout_sha256_prefix"]):
        print(f"::error::holdout changed ({digest[:16]}): metrics are not comparable")
        return 1

    cand, prod = evaluate("models/candidate.joblib"), deployed["metrics"]
    failures = []
    print(f"{'metric':<10}{'candidate':>11}{'deployed':>10}{'floor':>8}{'delta':>9}")
    for name, floor in (("accuracy", MIN_ACCURACY), ("macro_f1", MIN_MACRO_F1)):
        delta = cand[name] - prod[name]
        print(f"{name:<10}{cand[name]:>11.4f}{prod[name]:>10.4f}{floor:>8.2f}{delta:>+9.4f}")
        if cand[name] < floor:
            failures.append(f"{name} {cand[name]:.4f} below floor {floor:.2f}")
        if delta < -REGRESSION_TOLERANCE:
            failures.append(f"{name} regressed {delta:+.4f} vs {deployed['model_id']}")

    json.dump(cand, open("candidate_metrics.json", "w"), indent=2)
    for failure in failures:
        print(f"::error::QUALITY GATE FAILED: {failure}")
    if not failures:
        print("QUALITY GATE PASSED: eligible for merge and promotion")
    return 1 if failures else 0


if __name__ == "__main__":
    sys.exit(main())
```

- **The hash check runs first.** If the evaluation data changed, there is no honest comparison, and the gate says so instead of printing a delta.
- **All failures are collected**, not just the first, so the author fixes everything in one round.
- **`::error::`** lines become red annotations on the pull request in GitHub.
- **A small tolerance (0.005).** Demanding strict improvement would block refactors that change nothing; the tolerance lets only a meaningful drop trip the rule. Choosing it is a judgement about how much loss you will accept for a change's other benefits.

## Step 6: Promotion and the first deployed model (promote.py)

The regression rule needs a reference: the deployed model's scorecard, `deployed_metrics.json`. Only the promotion step writes it.

```python
"""After merge: record the candidate as the deployed model, which raises the bar.

Usage: python promote.py <model_id> <pr_number>
"""
import hashlib
import json
import shutil
import sys
from datetime import datetime, timezone

from quality_gate import evaluate

model_id, pr = sys.argv[1], sys.argv[2]
digest = hashlib.sha256(open("data/holdout.csv", "rb").read()).hexdigest()
record = {
    "model_id": model_id,
    "promoted_at": datetime.now(timezone.utc).isoformat(timespec="seconds"),
    "promoted_from_pr": pr,
    "holdout_sha256_prefix": digest[:16],
    "metrics": evaluate("models/candidate.joblib"),
}
shutil.copy("models/candidate.joblib", "models/deployed.joblib")
json.dump(record, open("deployed_metrics.json", "w"), indent=2)
print(json.dumps(record, indent=2))
```

Create the first production model:

```bash
python train.py
python promote.py ionosphere-rf-v1 bootstrap
```

{
  "model_id": "ionosphere-rf-v1",
  "promoted_at": "2026-10-06T13:54:02+00:00",

  "holdout_sha256_prefix": "d8849fe109a3c729",

## Step 7: Test the pipeline itself (tests/test\_pipeline.py)

```python
import hashlib
import json

import joblib
import pandas as pd

import train


def test_holdout_matches_the_deployed_record():
    digest = hashlib.sha256(open("data/holdout.csv", "rb").read()).hexdigest()
    assert digest.startswith(json.load(open("deployed_metrics.json"))["holdout_sha256_prefix"])


def test_train_and_holdout_do_not_overlap():
    tr, ho = pd.read_csv("data/train.csv"), pd.read_csv("data/holdout.csv")
    assert len(tr.merge(ho, how="inner")) == 0


def test_training_is_deterministic():
    train.main()
    first = joblib.load("models/candidate.joblib")
    train.main()
    second = joblib.load("models/candidate.joblib")
    holdout = pd.read_csv("data/holdout.csv")[first["features"]]
    assert (first["model"].predict(holdout) == second["model"].predict(holdout)).all()


def test_saved_model_carries_its_feature_list():
    train.main()
    bundle = joblib.load("models/candidate.joblib")
    assert len(bundle["features"]) == 34 - len(train.DROP_FEATURES)
```

```bash
python -m pytest -v
```

```text
4 passed
```

`test_training_is_deterministic` protects the gate against the most common cause of a **flaky** gate: the same commit passing on one run and failing on the next.

## Step 8: Try three pull requests locally

Each "pull request" is an edit to the settings in `train.py`, followed by what CI runs: `python train.py` then `python quality_gate.py`. Undo each edit before the next.

### PR #40: 500 trees instead of 300

Edit `N_ESTIMATORS = 500`.

```bash
python train.py && python quality_gate.py; echo "exit code: $?"
```

```text

macro_f1       0.9122    0.9122    0.90  +0.0000

```

No change at all on the holdout. It passes because it is **safe**, not because it is better. The gate answers "may this ship?", never "is this an improvement worth celebrating?".

### PR #42: drop the first five radar features ("they look noisy, and training gets faster")

Undo the previous edit. Set `DROP_FEATURES: list[str] = [f"Attribute{i}" for i in range(1, 6)]`.

```text
metric      candidate  deployed   floor    delta
accuracy       0.8977    0.9205    0.88  -0.0228
macro_f1       0.8853    0.9122    0.90  -0.0269
::error::QUALITY GATE FAILED: accuracy regressed -0.0228 vs ionosphere-rf-v1
::error::QUALITY GATE FAILED: macro_f1 0.8853 below floor 0.90
::error::QUALITY GATE FAILED: macro_f1 regressed -0.0269 vs ionosphere-rf-v1
exit code: 1
```

Look at **accuracy**: 0.8977 is **above** its 0.88 floor. A floor-only gate (Session 10) would have passed it, shipping a model 2.3 points worse than production. Only the regression rule catches it. The unit tests pass, the code is fine, training is faster, and nobody had to know what `Attribute3` measures.

### PR #41: limit trees to depth 3

Undo the previous edit. Set `MAX_DEPTH = 3`.

```text
metric      candidate  deployed   floor    delta
accuracy       0.9318    0.9205    0.88  +0.0113
macro_f1       0.9241    0.9122    0.90  +0.0119
QUALITY GATE PASSED: eligible for merge and promotion
exit code: 0
```

A genuine improvement: one more correct prediction out of 88. Merge it, then promote:

```bash
python promote.py ionosphere-rf-v2 41
```

```json
  "model_id": "ionosphere-rf-v2",
  "promoted_from_pr": "41",
  "metrics": {"accuracy": 0.9318, "macro_f1": 0.9241}
```

**The ratchet turned.** The next pull request must reach accuracy 0.9318 − 0.005 = **0.9268**, not 0.9155. PR #40 (500 trees, 0.9205) would now be blocked. That is the system working, not a bug, but expect to explain it to a frustrated contributor at least once.

Skip promotion and the ratchet silently stops: after a year of improvements, the gate would still compare every candidate with the first model and wave real regressions through. Commit `deployed_metrics.json` as part of promotion.

## Step 9: The GitHub Actions workflow

### .github/workflows/model-quality-gate.yml

```yaml
name: model-quality-gate

on:
  pull_request:
    branches: [main]

permissions:
  contents: read
  pull-requests: write          # to post the gate report as a PR comment

jobs:
  tests:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"
          cache: pip
      - run: pip install -r requirements.txt
      - run: python -m pytest -q

  quality-gate:
    needs: tests
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"
          cache: pip
      - run: pip install -r requirements.txt

      - name: Train candidate model
        run: python train.py

      - name: Compare with the floor and the deployed model
        run: |
          set -o pipefail
          python quality_gate.py | tee gate_report.txt

      - name: Post the gate report on the pull request
        if: always()
        uses: actions/github-script@v7
        with:
          script: |
            const fs = require('fs');
            const report = fs.existsSync('gate_report.txt')
              ? fs.readFileSync('gate_report.txt', 'utf8') : 'gate did not run';
            await github.rest.issues.createComment({
              issue_number: context.issue.number,
              owner: context.repo.owner,
              repo: context.repo.repo,
              body: '### Model quality gate\n```\n' + report + '\n```',
            });

      - name: Upload the candidate model
        if: success()
        uses: actions/upload-artifact@v4
        with:
          name: candidate-model
          path: |
            models/candidate.joblib
            candidate_metrics.json
```

| Line | Why |
| --- | --- |
| `needs: tests` | Broken code never reaches training |
| **`set -o pipefail`** | **Without it, the gate can never fail.** A pipeline's exit code is the **last** command's: `tee` succeeds, so the step succeeds even when `quality_gate.py` exits 1. Tested locally on PR #42: exit code 0 without `pipefail`, 1 with it. GitHub's default shell for `run:` does not set `pipefail` |
| `if: always()` on the comment | Steps after a failure are skipped by default. Without this, the report would be posted only when the gate **passes**: exactly backwards |
| `if: success()` on the upload | A rejected model is never published anywhere |
| `pull-requests: write` | Lets the workflow comment on the pull request; everything else stays read-only |

**Make it block merges:** in **Settings → Branches → Branch protection rules** for `main`, require the `quality-gate` status check (Session 10, Step 10). Without that, the check turns red above an enabled merge button.

Push the project as in Session 10, then open PR #42's change as a real pull request. The Checks tab shows `tests` **passing** and `quality-gate` **failing**, and the merge button is disabled. That combination is the whole argument for this session: correct software, worse model, blocked.

## When the gate itself is the problem

A gate that raises false alarms gets bypassed (an admin merge, a commit that removes the check), and once bypassing is normal, the gate is decoration.

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| The same commit passes, then fails | Something random: a split without `random_state`, an unseeded model, unpinned libraries | Freeze the split (Step 3); seed the model; pin `requirements.txt`. Do **not** widen the tolerance to hide it |
| Every candidate suddenly scores ~0.99 | Training reads the full dataset, holdout included | The `EXPECTED_TRAIN_ROWS` assert; check `trained_on` in the log |
| Gate never fails, even for bad models | `tee` without `pipefail` | `set -o pipefail` |
| `holdout changed` error | Someone regenerated `data/holdout.csv` | Restore it from Git; if the change was deliberate, re-baseline everything on the new holdout |
| Failure report missing on failed PRs | Comment step lacks `if: always()` | Add it |

## Common errors and fixes

| Error | Cause | Fix |
| --- | --- | --- |
| `FileNotFoundError: deployed_metrics.json` | No model promoted yet | `python train.py && python promote.py ionosphere-rf-v1 bootstrap` |
| `AssertionError: expected 263 rows` | Training data replaced or leaked | Restore `data/train.csv` from Git |
| `KeyError: "['Attribute3'] not in index"` | Scoring with the wrong feature list | Always score with the list saved in the model bundle |
| `Resource not accessible by integration` when commenting | Missing `pull-requests: write` | Add the `permissions:` block |
| Red check but merge still allowed | Check not required in branch protection | Require `quality-gate` on `main` |
