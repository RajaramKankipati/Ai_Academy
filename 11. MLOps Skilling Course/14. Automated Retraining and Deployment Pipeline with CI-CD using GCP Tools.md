# Automated Retraining and Deployment Pipeline with CI-CD using GCP Tools

## Overview

"Retrain every night and deploy the result" is one of the most common ways teams turn a working model into a broken one. New data is not automatically better data: a batch can be short, unusual for the season, or broken upstream, and the model trained on it still trains and still predicts. Nothing errors; the service just gets quietly worse.

In this session you build a **champion / challenger** retraining pipeline for a bike-demand model. Each new batch trains a **challenger**; it replaces the **champion** only if it is better, by a margin, on the **same frozen test set**. You run three cycles: one where the challenger wins, one where it wins again, and one where it loses and deployment is correctly skipped. Then you run the same pipeline in **Cloud Build** and deploy promoted models to **Vertex AI**.

```text
new batch ──► Cloud Build ──► tests ──► train challenger
                                              │
                         score champion AND challenger on the SAME frozen holdout
                                              │
                    better by ≥ 2%? ── no ──► SKIP: champion stays, endpoint untouched
                                              │ yes
                                              ▼
                         new model version in the registry ──► endpoint switches to it
```

By the end, you will be able to:

- Freeze a holdout set once and use it to judge every model.
- Remove holdout rows from training data safely, by key, with a guard.
- Write a promote/skip gate with a minimum improvement margin.
- Run the gate in Cloud Build and deploy promoted models as new versions in Vertex AI.
- Schedule the pipeline and alert on its **verdict**, not just on build failures.

**Prerequisites:** Python 3.11 and Session 10. Steps 1–7 are free and run locally. **Steps 8–12 need a Google Cloud project with billing enabled** and the [`gcloud` CLI](https://cloud.google.com/sdk/docs/install). The Vertex AI endpoint bills per hour; do Step 12 (clean up) the same day.

**Dataset:** [UCI Seoul Bike Sharing Demand](https://archive.ics.uci.edu/dataset/560/seoul+bike+sharing+demand), 8,760 hourly records (one full year, Dec 2017 – Nov 2018): bikes rented per hour, weather, hour, season, holiday. Its strong **seasons** let us simulate data arriving month by month, and show why the newest data is not always the best training data. It is downloaded automatically by the code.

## Step 4: Features and safe holdout exclusion (src/features.py)

```python
"""Turn raw hourly rows into model inputs. The same code for every batch."""
import pandas as pd

TARGET = "Rented Bike Count"
KEY = ["Date", "Hour"]                      # identifies one row, whatever file it is in
SEASONS = ["Autumn", "Spring", "Summer", "Winter"]


def featurize(frame):
    X = frame.copy()
    date = pd.to_datetime(X["Date"])
    X["month"] = date.dt.month
    X["weekday"] = date.dt.weekday
    X["is_weekend"] = (X["weekday"] >= 5).astype(int)
    # Fixed category list: every batch gets the same 4 season columns,
    # even a batch that contains only one season.
    for season in SEASONS:
        X[f"season_{season}"] = (X["Seasons"] == season).astype(int)
    X["holiday"] = (X["Holiday"] == "Holiday").astype(int)
    X["functioning"] = (X["Functioning Day"] == "Yes").astype(int)
    X = X.drop(columns=["Date", "Seasons", "Holiday", "Functioning Day", TARGET])
    return X, frame[TARGET]


def exclude_holdout(batch, holdout):
    """Drop every holdout hour from a training batch, matching on KEY (never on row position)."""
    marked = batch.merge(holdout[KEY].assign(_in_holdout=1), on=KEY, how="left")
    train = marked[marked["_in_holdout"].isna()].drop(columns="_in_holdout")
    # Removing zero rows almost always means the KEY columns did not match (e.g. date formats).
    assert len(train) < len(batch), "holdout exclusion removed zero rows -- check KEY formats"
    return train
```

Two silent bugs this file prevents:

- **Different columns per batch.** `pd.get_dummies(Seasons)` on a winter-only batch creates only `Seasons_Winter`. A model trained on it, scored on a holdout with all four seasons, sees shifted columns and returns a nonsense score that looks like a real number. Writing the four season columns explicitly gives every batch the same columns.
- **Holdout rows leaking into training.** A natural first attempt is `batch[~batch.index.isin(holdout.index)]`. But every `pd.read_csv` gives a **fresh** row index (0, 1, 2, ...), so this compares unrelated row numbers. On the Sep–Nov batch it removes the first 1,200 rows of the file (not the holdout hours) and leaves 122 holdout hours in the training data. The model then scores MAE **32** on those memorised hours versus about 260 on the rest: it is partly sitting an exam it has already seen. Matching on the **key** (`Date` + `Hour`) is correct, and the `assert` catches the other silent failure: a key that never matches (say, `2018-09-01` vs `01/09/2018`) removes nothing.

### tests/test\_features.py

```python
import pandas as pd
import pytest

from src.features import exclude_holdout, featurize


def rows(dates_hours, season="Winter"):
    return pd.DataFrame([{
        "Date": d, "Hour": h, "Rented Bike Count": 100, "Temperature": 1.0,
        "Humidity": 50, "Wind speed": 1.0, "Visibility": 2000,
        "Dew point temperature": -5.0, "Solar Radiation": 0.0, "Rainfall": 0.0,
        "Snowfall": 0.0, "Seasons": season, "Holiday": "No Holiday", "Functioning Day": "Yes",
    } for d, h in dates_hours])


def test_every_batch_gets_the_same_columns():
    winter, _ = featurize(rows([("2018-01-01", 0)], "Winter"))
    summer, _ = featurize(rows([("2018-07-01", 0)], "Summer"))
    assert list(winter.columns) == list(summer.columns)


def test_holdout_hours_are_removed_by_key_not_position():
    batch = rows([("2018-09-01", 0), ("2018-09-01", 1), ("2018-09-01", 2)])
    holdout = rows([("2018-09-01", 2)])            # its row position is 0, its key is hour 2
    train = exclude_holdout(batch, holdout)
    assert train["Hour"].tolist() == [0, 1]


def test_key_format_mismatch_is_caught():
    batch = rows([("2018-09-01", 0), ("2018-09-01", 1)])
    holdout = rows([("01/09/2018", 0)])            # same hour, different date format
    with pytest.raises(AssertionError, match="removed zero rows"):
        exclude_holdout(batch, holdout)
```

## Step 5: Freeze the holdout and create the batches (src/prepare\_batches.py)

```python
"""Turn one year of data into a frozen holdout and three batches that 'arrive' over time."""
import pandas as pd
from ucimlrepo import fetch_ucirepo

from src.features import TARGET

df = fetch_ucirepo(id=560).data.original
df["Date"] = pd.to_datetime(df["Date"], format="%d/%m/%Y").dt.strftime("%Y-%m-%d")
df = df.sort_values(["Date", "Hour"]).reset_index(drop=True)
print(f"{len(df)} hourly rows, {df.Date.min()} to {df.Date.max()}")
print(df.groupby("Seasons")[TARGET].mean().round(0).to_string())

# Frozen holdout: 1,200 random hours from the WHOLE year. Created once, never redrawn.
holdout = df.sample(1200, random_state=42).sort_values(["Date", "Hour"])
holdout.to_csv("store/holdout.csv", index=False)

batches = {
    "data/batch_0_dec_feb.csv": df[df.Date < "2018-03-01"],
    "data/batch_1_mar_aug.csv": df[(df.Date >= "2018-03-01") & (df.Date < "2018-09-01")],
    "data/batch_2_sep_nov.csv": df[df.Date >= "2018-09-01"],
}
print()
for path, batch in batches.items():
    batch.to_csv(path, index=False)          # batches still contain holdout hours
    print(f"{path:<26} {len(batch):>5} rows   mean demand {batch[TARGET].mean():6.0f}")
print(f"{'store/holdout.csv':<26} {len(holdout):>5} rows   mean demand {holdout[TARGET].mean():6.0f}")
```


```text
8760 hourly rows, 2017-12-01 to 2018-11-30
Seasons
Autumn     820.0
Spring     730.0
Summer    1034.0
Winter     226.0

data/batch_0_dec_feb.csv    2160 rows   mean demand    226
data/batch_1_mar_aug.csv    4416 rows   mean demand    882
data/batch_2_sep_nov.csv    2184 rows   mean demand    820
store/holdout.csv           1200 rows   mean demand    694
```

- **Summer demand is 4.5× winter demand.** A model trained on one season learns a very different pattern from one trained on another.
- **The holdout spans the whole year**, so its mean (694) is near the yearly average, not near any single batch. A holdout drawn from the newest batch would flatter whichever model was trained most recently, and the gate would become a rubber stamp.
- **The holdout is created once and stored.** The retraining script only ever **reads** it. If each run drew its own holdout, a challenger could always be made to look better.

## Step 6: The retraining gate (src/retrain.py)

```python
"""Train a challenger on a new batch, compare it with the champion, promote only if better.

Usage: python -m src.retrain --data data/batch_1_mar_aug.csv [--min-improvement 0.02]

The store folder holds holdout.csv and, once there is one, the champion:
  store/champion/model.joblib   the model
  store/champion/champion.json  its holdout MAE and where it came from
"""
import argparse
import json
import os

import joblib
import pandas as pd
from sklearn.ensemble import GradientBoostingRegressor
from sklearn.metrics import mean_absolute_error

from src.features import exclude_holdout, featurize

p = argparse.ArgumentParser()
p.add_argument("--data", required=True)
p.add_argument("--store", default="store")
p.add_argument("--min-improvement", type=float, default=0.02)
args = p.parse_args()

holdout = pd.read_csv(f"{args.store}/holdout.csv")
batch = pd.read_csv(args.data)

train = exclude_holdout(batch, holdout)

X_train, y_train = featurize(train)
X_hold, y_hold = featurize(holdout)

challenger = GradientBoostingRegressor(n_estimators=400, max_depth=4,
                                       learning_rate=0.06, random_state=0)
challenger.fit(X_train, y_train)
challenger_mae = mean_absolute_error(y_hold, challenger.predict(X_hold))

champion_dir = f"{args.store}/champion"
if os.path.exists(f"{champion_dir}/model.joblib"):
    champion = joblib.load(f"{champion_dir}/model.joblib")
    champion_mae = mean_absolute_error(y_hold, champion.predict(X_hold))
    improvement = (champion_mae - challenger_mae) / champion_mae
    verdict = "PROMOTE" if improvement >= args.min_improvement else "SKIP"
else:
    champion_mae, improvement, verdict = None, None, "PROMOTE"   # first model ever

report = {
    "data": os.path.basename(args.data),
    "rows_in_batch": len(batch),
    "holdout_rows_removed": len(batch) - len(train),
    "n_train": len(train),
    "champion_mae": None if champion_mae is None else round(champion_mae, 1),
    "challenger_mae": round(challenger_mae, 1),
    "improvement": None if improvement is None else round(improvement, 3),
    "verdict": verdict,
}
print(json.dumps(report, indent=2))

if verdict == "PROMOTE":
    os.makedirs(champion_dir, exist_ok=True)
    joblib.dump(challenger, f"{champion_dir}/model.joblib")
    with open(f"{champion_dir}/champion.json", "w") as f:
        json.dump(report, f, indent=2)
with open("report.json", "w") as f:
    json.dump(report, f, indent=2)
```

What each part does:

- **Both models are scored on the same frozen holdout.** The champion is re-scored every run, so the comparison is always like for like.
- **`--min-improvement 0.02`**: the challenger must cut MAE by at least 2%, not just by any amount. Two models trained on similar data differ a little by chance; without a margin, the pipeline would swap models on noise. The margin is a command-line option because it is an operational policy you may tune without changing code.
- **The first run has no champion**, so it promotes automatically.
- **`report.json`** is written every run, promoted or not. The next steps read it.

## Step 9: Register and deploy promoted models (src/deploy\_vertex.py)

```python
"""Store the new champion in GCS, register it as a new model version, and switch the endpoint.

Usage: python -m src.deploy_vertex --project P --region R --bucket B --build-id ID
"""
import argparse
import glob
import os

from google.cloud import aiplatform, storage

SKLEARN_IMAGE = "us-docker.pkg.dev/vertex-ai/prediction/sklearn-cpu.1-3:latest"

p = argparse.ArgumentParser()
for name in ("--project", "--region", "--bucket", "--build-id"):
    p.add_argument(name, required=True)
args = p.parse_args()

# 1. Copy the champion to a folder unique to this build, so old versions keep their files.
bucket = storage.Client(project=args.project).bucket(args.bucket)
version_prefix = f"bike/models/{args.build_id}"
for path in glob.glob("store/champion/*"):
    name = os.path.basename(path)
    bucket.blob(f"{version_prefix}/{name}").upload_from_filename(path)
    bucket.blob(f"bike/champion/{name}").upload_from_filename(path)   # next run's champion
print(f"champion stored at gs://{args.bucket}/{version_prefix}/")

# 2. Register it as a new version of the "bike-demand" model.
aiplatform.init(project=args.project, location=args.region)
existing = aiplatform.Model.list(filter='display_name="bike-demand"')
model = aiplatform.Model.upload(
    display_name="bike-demand",
    parent_model=existing[0].resource_name if existing else None,
    artifact_uri=f"gs://{args.bucket}/{version_prefix}/",
    serving_container_image_uri=SKLEARN_IMAGE,
    is_default_version=True,
)
print(f"registered {model.resource_name} version {model.version_id}")

# 3. Deploy it with 100% of traffic, then remove the old version from the endpoint.
endpoints = aiplatform.Endpoint.list(filter='display_name="bike-demand-endpoint"')
endpoint = endpoints[0] if endpoints else aiplatform.Endpoint.create(
    display_name="bike-demand-endpoint")
old_ids = [m.id for m in endpoint.list_models()]
model.deploy(endpoint=endpoint, machine_type="n1-standard-2",
             min_replica_count=1, max_replica_count=1, traffic_percentage=100)
for deployed_id in old_ids:
    endpoint.undeploy(deployed_model_id=deployed_id)
print(f"endpoint {endpoint.resource_name} now serves version {model.version_id}")
```

- **A folder per build (`bike/models/<build id>/`).** If every promotion overwrote one `champion/model.joblib`, every registered version would point at the same file, and rolling back to version 1 would silently load version 3. Unique folders keep each version's file intact.
- **`parent_model`** makes each promotion **version 2, 3, ...** of one model in the Vertex AI Model Registry, instead of an unrelated new model each time.
- **Deploy first, then undeploy the old one**, so there is never a moment with nothing serving.

## Step 10: The Cloud Build pipeline (cloudbuild.yaml)

```yaml
steps:
  # 1. Bring the pipeline's state into the build: holdout, current champion, new batch.
  - id: fetch-state
    name: gcr.io/google.com/cloudsdktool/cloud-sdk:slim
    entrypoint: bash
    args:
      - -c
      - |
        mkdir -p store data
        gcloud storage cp gs://${_BUCKET}/bike/holdout.csv store/
        gcloud storage cp -r gs://${_BUCKET}/bike/champion store/ || echo "no champion yet"
        gcloud storage cp ${_DATA_URI} data/batch.csv

  # 2. Install once. --user puts packages in $HOME, which every later step shares.
  - id: install
    name: python:3.11-slim
    entrypoint: pip
    args: [install, --user, --quiet, -r, requirements.txt]

  # 3. Unit tests: never retrain with broken feature code.
  - id: test
    name: python:3.11-slim
    entrypoint: python
    args: [-m, pytest, -q]

  # 4. Train the challenger and run the champion/challenger gate.
  - id: retrain-and-gate
    name: python:3.11-slim
    entrypoint: python
    args: [-m, src.retrain, --data, data/batch.csv, --min-improvement, "${_MIN_IMPROVEMENT}"]

  # 5. Deploy only if the gate said PROMOTE.
  - id: promote-if-better
    name: python:3.11-slim
    entrypoint: bash
    args:
      - -c
      - |
        if grep -q '"verdict": "PROMOTE"' report.json; then
          python -m src.deploy_vertex --project $PROJECT_ID --region ${_REGION} \
              --bucket ${_BUCKET} --build-id $BUILD_ID
        else
          echo "SKIP: challenger not better by ${_MIN_IMPROVEMENT}; champion kept, endpoint untouched"
        fi

substitutions:
  _BUCKET: your-mlops-bucket
  _REGION: us-central1
  _DATA_URI: gs://your-mlops-bucket/bike/incoming/batch_1_mar_aug.csv
  _MIN_IMPROVEMENT: "0.02"

options:
  logging: CLOUD_LOGGING_ONLY
timeout: 3600s
```

| Part | Meaning |
| --- | --- |
| Each step's `name` | The container image the step runs in. Steps share the `/workspace` folder (your code plus files earlier steps wrote) |
| `--user` install | Each step is a fresh container, but `$HOME` is shared between steps, so packages installed there once are visible to every later step |
| `${_BUCKET}`, `${_DATA_URI}`, ... | **Substitutions**: values you can change per run without editing the file |
| `$PROJECT_ID`, `$BUILD_ID` | Built-in substitutions Cloud Build fills in |
| Step 3 before step 4 | A bug in `features.py` fails the build **before** any model is trained or deployed |

The third prints `SKIP: challenger not better by 0.02; champion kept, endpoint untouched`.

Then check:

```bash
gcloud builds list --limit=3 --format="table(id,status,createTime,duration)"
gcloud ai models list --region=us-central1 --filter="display_name=bike-demand"
```

**All three builds show `SUCCESS`**, including the one that skipped. That is correct, and it is the most important thing to understand about monitoring this pipeline: **a skipped promotion is a green build.** If you alert only on failed builds, you will never learn that retraining has rejected every model for the last three months and your "automatically retrained" model is now eight months old.

**Alert on the verdict.** In **Logging → Logs Explorer**, this query finds every skip:

```text
resource.type="build" AND textPayload:"SKIP: challenger not better"
```

Click **Create metric** to turn it into a log-based metric, then create an alert in Cloud Monitoring when it counts, say, 3 skips in 3 weeks.

### Run it on a schedule

1. Push this project to a GitHub repository.
2. In **Cloud Build → Triggers → Connect repository**, connect it.
3. **Create trigger**: event **Manual invocation**, your repository and branch `main`, configuration `cloudbuild.yaml`, and set `_DATA_URI` to where new data lands each week (e.g. `gs://your-mlops-bucket/bike/incoming/latest.csv`).
4. On the trigger's row, choose **Run on schedule**, and set e.g. `0 2 * * 0` (Sundays 02:00). Cloud Build creates the Cloud Scheduler job for you.

Scheduled and manual runs use the **same** `cloudbuild.yaml`, so the same tests and the same gate. Never give the unattended path a weaker check: unattended is exactly when you most need it.

## Common errors and fixes

| Error | Cause | Fix |
| --- | --- | --- |
| `AssertionError: holdout exclusion removed zero rows` | `Date` formats differ between batch and holdout | Write every file with `prepare_batches.py` (dates as `YYYY-MM-DD`) |
| A challenger scores an MAE far better than any before | Holdout rows leaked into training | Exclude by key with `exclude_holdout`, never by row index |
| `ValueError: ... feature names ... ` when scoring the champion | Columns differ between batches | Keep the fixed season list in `featurize` |
| `fetch-state` fails: `No URLs matched ... holdout.csv` | Holdout not uploaded | `gcloud storage cp store/holdout.csv gs://.../bike/holdout.csv` |
| `test` step: `ModuleNotFoundError` | `install` step failed, or `--user` missing | Read the install step's log; keep `--user` |
| `PERMISSION_DENIED` in `promote-if-better` | Build service account lacks Vertex AI or Storage roles | Grant the roles in Step 8 |
| Endpoint fails to start after promotion | Model saved with a scikit-learn other than 1.3.x | Keep `scikit-learn==1.3.2` in `requirements.txt` |
| Build `SUCCESS` but nothing deployed | The gate said `SKIP` (correct) | Read the `retrain-and-gate` JSON; alert on the verdict |
